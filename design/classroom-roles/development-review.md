# 1인 1역 개발·검토 기록

## 검토 방식

아래 6명은 설계 가설을 점검하기 위한 가상 인물이다. 실제 교사 인터뷰나 외부 코드 리뷰를 진행한 것으로 해석하지 않는다. 코드 리뷰와 자동 검사는 개발 에이전트가 직접 수행했다.

## 2단계: 화면·구현 모의 검토

| 가상 담임 | 의견 | 반영한 설계 |
| --- | --- | --- |
| 김서연(5학년, 4년차) | 공용 태블릿에서는 다음 학생을 위해 제출 후 첫 화면으로 돌아가야 한다 | 저장 확인 메시지와 이름 선택 화면 복귀 |
| 박준호(5학년, 12년차) | 월마다 주소를 다시 보내면 번거롭다 | 학급 공용 토큰 유지, 다음 기간 자동 적용 |
| 이하은(5학년, 20년차) | 배정 중 역할 자리가 모자라면 앞뒤 화면을 오가지 않아야 한다 | 배정 2단계에서 역할 추가·정원 조정, 남은 자리 표시 |
| 정민재(6학년, 7년차) | 학생 입력인지 교사 정정인지 구분해야 한다 | 입력 출처 표시, 날짜별 정정 및 미기록 초기화 |
| 최지윤(6학년, 16년차) | 공개 화면에 학생끼리의 비교가 기본으로 나오지 않아야 한다 | 상태 기본 숨김, 누가 기록은 교사 전용, 표시용 이름 가리기 |
| 한도현(6학년, 26년차) | 6개 메뉴는 데스크톱에서 한눈에 들어와야 한다 | 3열×2행, 오늘 요약 아래에 기능만 배치 |

## 3단계: 예외 상황·검증 모의 검토

| 가상 담임 | 점검 의견 | 반영/검증 |
| --- | --- | --- |
| 김서연 | 실수로 두 번 눌러도 기록 수가 늘면 안 된다 | 날짜·학생·기간 고유 키 및 갱신 RPC, 재제출 E2E |
| 박준호 | 여러 탭에서 설정하면 조용히 덮어쓰지 않아야 한다 | 설정 버전 비교, DB 행 잠금, 409 오류 안내 |
| 이하은 | 명단 중복·정원 초과·기간 겹침은 확정 전에 잡아야 한다 | 공통 클라이언트/서버 검증, 입력 유지 오류 안내 |
| 정민재 | 결석과 공휴일을 실패로 집계하면 안 된다 | 해당 없음·제외일·역할 요일, 미기록과 미실천 분리 |
| 최지윤 | 링크가 학급 밖에 알려졌을 때 끊을 수 있어야 한다 | 공유 중지·토큰 재발급, 이전 링크 거부, 공개 응답 필드 제한 |
| 한도현 | 학생 수가 많아도 한 달 기록이 빠지면 안 된다 | 서버 500행 단위 페이지 조회, 1,050행 반환 회귀 검사 |

## 코드 리뷰에서 확인·수정한 사항

- 입력 검증의 TypeScript narrowing 오류 수정. 프런트엔드와 Deno 서버를 별도로 검사한다.
- 공개 응답은 학생/역할 객체를 그대로 펼치지 않고 필요한 필드만 선택한다. 추가된 교사 전용 필드가 우연히 공개되지 않게 한다.
- PostgREST 기본 행 수 제한으로 월간 기록이 잘리는 것을 막기 위해 페이지별로 조회한다.
- 동일 날짜 중복 제출은 upsert한다. 설정 변경과 기록 저장 간 경쟁은 버전 검사 + DB 행 잠금으로 막는다.
- 공개 입력은 KST 오늘·활성 배정·실천일만 허용한다. 비실천·과거·미래·다른 학생 식별자 위조 요청을 검사한다.
- 암호화 키·요청 제한 확인에 실패하면 저장/공개를 중단한다. 요청 원문·학생 이름·토큰을 서버 로그에 남기지 않는다.
- 폼 라벨은 고유 id와 htmlFor로 연결하고, 학생별 역할 select에 명시적 접근 가능 이름을 부여한다.
- 전체 단위 테스트의 기존 Windows 경로 비교 오류를 발견해 `join()`으로 수정했다. 기존 개인 QR 기능의 동작은 바꾸지 않았다.
- 학생 화면은 자기보고이며 본인 인증이 아니다. 다른 학생 선택을 기술적으로 막는다고 안내하지 않는다.
- 의존성 감사에서 기존 Vitest 개발 도구의 파일 경로 검사 취약점이 발견되어 4.1.11 패치로 갱신했다. [Vitest 공식 보안 권고](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9)를 확인했으며 운영 앱 의존성은 바꾸지 않는다.

## 4단계: 배포 인수 모의 검토

| 가상 담임 | 운영 인수 의견 | 반영·실제 확인 결과 |
| --- | --- | --- |
| 김서연 | 공용 기기에서 저장하면 다음 학생이 바로 쓰고 교사도 확인할 수 있어야 한다 | 운영 학생 화면 제출 후 명단 복귀, 교사 새로고침에 했어요 반영 확인 |
| 박준호 | 데모 저장을 기기 간 동기화로 안내하면 안 된다 | 교사 인증 브라우저와 독립 비로그인 학생 컨텍스트 사이의 운영 서버 저장·조회 확인 |
| 이하은 | 다음 역할을 준비해도 이전 학생 이름·역할이 달라지면 안 된다 | 운영 API에서 다음 기간 추가, 과거 스냅샷 유지 및 과거 변경 거부 확인 |
| 정민재 | 실제 학생 자료를 넣기 전에 교사별 권한 분리가 검증되어야 한다 | 가상 교사 두 명으로 소유자 격리, RLS, 직접 쓰기/RPC 차단, 교사 정정 확인 |
| 최지윤 | 공개 상태 숨김과 공유 중지·이전 링크 차단이 실제로 작동해야 한다 | API 공개 필드 제한과 기본 상태 숨김, 운영 UI 공유 중지·재발급 후 이전 링크 거부 확인 |
| 한도현 | 홈 메뉴와 월간 상세 동선이 운영 주소에서도 같아야 한다 | 운영 홈 6개 기능, 설정 명단 → 2단계 배정 → 학생 제출 → 교사 월간 상세 확인 |

운영 검증은 실제 교사·학생이 아닌 생성한 가상 계정/명단을 사용했다. 학생 화면은 Chrome의 390×844 모바일 뷰포트이며 물리적인 교실 태블릿을 직접 시험한 것은 아니다. Google OAuth 팝업 자체는 자동화하지 않았고 시험 계정의 정상 Supabase 세션으로 교사 화면을 검사했다.

운영 인수 중 저장 성공 안내와 후속 로딩 안내가 동시에 표시되어 테스트의 단일 `status` 선택자가 실패했다. 실제 저장 실패가 아님을 오류 내용으로 확인하고, 저장 메시지로 범위를 좁히는 회귀 검사로 수정했다. 수정 후 실제 서버·운영 브라우저 7개 검사 그룹과 데모 E2E 22개가 모두 통과했다. 최종 가상 계정 2개와 종속 자료는 정리했다.
