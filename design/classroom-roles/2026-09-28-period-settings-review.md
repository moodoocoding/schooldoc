# 1인 1역 운영 기간 수정·삭제 검토

## 변경 전 관찰

- 진행이 끝난 기간은 설정 목록에서 사라져 수정할 수 없었다.
- 시작한 기간의 시작일을 비활성화하고 종료일에도 오늘 이전 날짜를 막아, 잘못 입력한 기간을 바로잡을 수 없었다.
- 확정한 기간을 삭제하는 경로가 없었다.

## 프로파일별 판단과 반영

| 관점 | 판단·근거 | 반영 | 남은 위험 |
| --- | --- | --- | --- |
| 웹디자이너 | 날짜 입력의 비활성 상태와 숨겨진 과거 기간이 실제 편집 범위를 파악하기 어렵게 한다. | 과거 기간도 같은 선택 목록에 표시하고 두 날짜 입력을 동일한 형태로 열었다. 삭제는 날짜 바로 아래 별도 위험 색상 버튼으로 분리했다. | 기간이 많아지면 기본 select에서 날짜 범위를 찾는 데 시간이 걸릴 수 있다. |
| UX 디자이너 | 교사는 지난 기간의 오입력을 수정하거나 불필요한 기간을 지워야 한다. 기록을 잃는 삭제는 예기치 않은 결과다. | 과거 날짜를 허용하고, 삭제 확인을 거치며, 기록이 있는 날짜를 제외하거나 기간을 삭제하려 하면 이유를 표시한다. | 이미 기록된 기간 전체를 없애야 할 경우에는 별도 기록 정리 절차가 필요하다. |
| UI 디자이너 | 비활성 입력은 편집 불가능하다는 잘못된 신호를 주고, 삭제 동작에는 분명한 이름과 상태가 필요하다. | 접근 가능한 `운영 시작일`·`운영 종료일` 라벨을 유지하고 `이 운영 기간 삭제` 버튼에 busy 비활성 상태를 적용했다. | 브라우저 기본 날짜 선택기의 표현은 OS마다 다르므로 직접 입력도 가능하게 유지한다. |

## 구현 후 검증

- 데스크톱 전체 페이지 캡처에서 날짜 입력, 삭제 버튼, 제외일 달력, 저장 버튼의 배치와 빈 공간을 확인했다.
- 모바일 390px 전체 페이지 캡처와 195px 가로 넘침 검사, 달력 접근성 검사를 통과했다.
- 가상 학생 기록으로 과거 기간 저장·선택·삭제, 기록이 있는 기간의 삭제 거부, 기록일을 벗어나는 날짜 변경 거부를 검증했다.
- 로컬 메모리 PostgreSQL에서 소유자·버전 검사와 기록 보호가 한 트랜잭션 안에서 동작함을 검증했다.
