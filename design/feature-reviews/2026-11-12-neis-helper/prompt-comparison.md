# 교과평어 작성 흐름과 프롬프트 비교 (codex)

확인일: 2026-11-12. 사용자가 제공한 Gemini 프롬프트, 두 평가계획 PDF의 앞부분 표, EduNote 공개 소스를 비교했다.
EduNote 기준 커밋: `729fc8c3cd934691dec2a03b6e10504fa5ab59ae`.
실제 학생 성적 파일은 제공되지 않았으며 같은 자료를 이용한 생성 결과 A/B 시험은 수행하지 않았다.
아래는 입력 구조·프롬프트·검증 코드의 정적 비교이며 생성 품질의 실측 순위가 아니다.

## 결론

초등 교과평어 일괄 작성에는 사용자의 **평가계획 → 나이스 성적 → 평어** 흐름이 적합하다.
EduNote에서는 사실성 지시와 성적 누락 방지 검증, 결과 편집·분량 확인 방식을 참고할 가치가 있다.
핵심 보완은 평가계획의 성취기준·평가요소·수준별 평가기준을 별도 보존하고 나이스의 해당 평가 결과와 연결하는 것이다.
학생별 추가 관찰 메모는 선택 사항이며 모든 학생에게 입력을 강제하지 않는다.

### EduNote의 중요한 구조적 차이

- [평가계획 분석 함수](https://github.com/codersongpro/edunote/blob/729fc8c3cd934691dec2a03b6e10504fa5ab59ae/src/renderer/services/geminiService.ts#L1563)는 성취기준 코드·본문이나 ◎○△별 평가기준을 별도 필드로 추출하지 않는다. 과제 문자열에 일부가 포함될 가능성은 있지만 전체 기준의 보존·연결을 보장하지 않는다.
- [나이스 가져오기](https://github.com/codersongpro/edunote/blob/729fc8c3cd934691dec2a03b6e10504fa5ab59ae/src/renderer/components/SubjectGenerator.tsx#L479)는 학생 이름을 집합으로 합쳐 정렬하며 이름으로 연결한다. 원본 번호순 전수 대조와 다르며 동명이인이 합쳐질 위험이 있다. 실제 동명이인 자료로 재현한 결과는 아니다.
- 같은 화면의 [계획 분석 처리](https://github.com/codersongpro/edunote/blob/729fc8c3cd934691dec2a03b6e10504fa5ab59ae/src/renderer/components/SubjectGenerator.tsx#L603)와 나이스 가져오기는 각자 과제 목록을 구성한다. 평가계획과 나이스 평가 열을 성취기준·수준별 평가기준까지 연결하는 전용 결합 구조는 확인되지 않았다.
- [사실성 지시](https://github.com/codersongpro/edunote/blob/729fc8c3cd934691dec2a03b6e10504fa5ab59ae/src/renderer/services/geminiService.ts#L240)와 [교과 생성 요청](https://github.com/codersongpro/edunote/blob/729fc8c3cd934691dec2a03b6e10504fa5ab59ae/src/renderer/services/geminiService.ts#L448)은 근거가 부족할 때 분량을 줄이도록 지시한다. 이는 프롬프트상의 예방책이며 사실 정확성을 자동 보증하는 장치는 아니다.
- [나이스 분석 지시](https://github.com/codersongpro/edunote/blob/729fc8c3cd934691dec2a03b6e10504fa5ab59ae/src/renderer/services/geminiService.ts#L1593)와 [성적 검증](https://github.com/codersongpro/edunote/blob/729fc8c3cd934691dec2a03b6e10504fa5ab59ae/src/renderer/lib/neisGradeValidation.ts)은 빈 성적·배열 길이·값을 검사한다. 분석기가 정상값을 잘못 읽는 경우까지 원본과 자동 대조한다고 해석하면 안 된다.

확인한 교과 화면의 생성 경로는 `generateSubjectReport`다. 검토한 경로에서는 별도의 교과평어 전용 프롬프트를 확인하지 못했다.

## 사용자 평가계획에서 확인한 점

원본은 수정하지 않았다. 표 구조 확인 범위는 2025 파일 1~3쪽, 2026 파일 1~3쪽이며 전체 문서의 내용 감수는 하지 않았다.

- 2025학년도 4학년 2학기 파일은 48쪽이며, 성취기준·평가요소·◎○△별 평가기준이 있다. 3쪽의 사각형 분류·소수 계산 등은 수준에 따른 수행 범위를 이미 서술한다.
- 2026학년도 5학년 2학기 파일은 65쪽이며 같은 종류의 기준 표가 있다. 3쪽 평균 평가의 ○ 기준은 평균 의미 이해와 주어진 자료의 평균 계산, △ 기준은 간단한 자료의 평균 계산이다. △를 곧바로 친구 도움이나 꾸준한 노력으로 바꿀 근거는 없다.
- 사용자 예시의 `[6국05-04]` 내용과 2026 파일 1쪽의 같은 코드 본문이 다르다. 파일에는 작품의 인상적인 부분을 중심으로 의견을 나누는 기준이 적혀 있다. 연도·교육과정에 따른 원문 코드와 본문을 함께 보존해야 한다. 이 비교는 국가 교육과정 원문과의 정확성 검증을 뜻하지 않는다.

## 기존 프롬프트에서 정리할 충돌

1. '3단계'라고 안내하지만 실제는 4단계다. 자료 확인 두 번, 분량 선택, 결과 생성으로 일치시킨다.
2. 금지어의 '비범함·매우'가 뒤의 권장 칭찬 표현에도 들어 있다. 막연한 칭찬을 늘리는 대신 평가기준에 따른 실제 수행을 서술한다.
3. 제공된 예시는 성취기준과 ◎만으로 가족 대화·유머·감정 이해 등의 개별 활동을 확장한다. 예시는 문체에만 사용하고 예시의 사건을 학생에게 옮기지 않는다.
4. 모든 첫 단어·첫 3글자의 절대적 차별화는 같은 평가 결과를 억지로 다르게 만들 수 있다. 반복 점검은 유지하되 사실과 평가 의미가 우선이다.
5. 긴 목표 글자 수를 채우기 위해 새로운 행동을 추가하지 않는다. 200/300/400자는 목표이며 근거가 부족하면 짧게 작성하고 사유를 표시한다.
6. 표·정렬·학생 정보·글자 수는 앱이 구성한다. AI에는 해당 학생의 평어 본문과 근거 연결을 맡긴다.

## 2026-11-12 사용자 동의가 확인된 설계 기준

사용자는 사실성 규칙과 성적 누락 검사의 설명을 듣고 필요성에 동의했다.
이는 아래 설계 원칙에 대한 동의이며 네 생성 기능 전체의 구현·운영 배포 완료를 의미하지 않는다.

- **사실성:** 계획의 관련 평가기준과 학생의 해당 평가 결과 범위에서 초안을 만든다. 도움·노력·성장·리더십·구체적 사건을 성적만으로 추정하지 않는다. 추가 관찰이 있으면 그 내용까지 활용한다.
- **누락 방지:** `◎ / 빈칸 / △`의 열과 빈칸을 그대로 보존한다. 임의 상향·앞당김·평균 성적 대입을 금지한다. 미확인 항목이 있는 학생·평가 범위는 교사 확인 후 생성한다.
- **원본 대조:** 번호·학생 식별자·평가 열을 유지하고 명단 전체를 보여 준다. 이름만으로 학생을 합치지 않는다. OCR 결과의 형식 검증과 원본 확인을 구분한다.
- **단순한 사용 흐름:** 평가계획 업로드·확인 → 나이스 성적 업로드·대조 → 목표 분량 선택·생성 → 교사 수정·확정·복사/Excel 출력. 모든 학생에게 별도 관찰 서술을 요구하지 않는다.

위 비교를 작성한 시점에는 평가계획·성적 연결, 생성 서버, 결과 편집기를 구현하지 않았으며 Neis Helper 이름과 네 영역의 안내 화면까지 준비한 상태였다.

후속 요청에 따라 2026-11-12 교과학습발달상황의 단계별 작성 화면·검증·생성 서버를 로컬 구현했다. [후속 구현 및 검증 기록](subject-workflow-review.md)을 참고한다. 나머지 세 영역과 운영 배포는 이 구현에 포함하지 않는다.
