# 교과학습발달상황 구현 검토 (codex)

사용자 요청: 평가계획과 나이스 성적을 올려 누락·오연결을 확인하고 근거에 맞는 평어를 생성한다. 한 단계에서는 한 가지 판단을 요구한다.
AI의 모의 검토이며 실제 전문가·교사 인터뷰가 아니다.

## 구현 전

| 관점 | 판단·근거 | 구현 방향과 남은 위험 |
| --- | --- | --- |
| 웹디자인 | 업로드·기준·명단·생성 옵션을 한 화면에 놓으면 정보 밀도가 높다. | 현재 단계 제목과 대표 진행 버튼을 하나만 둔다. 검토 대상 한 항목과 원본을 구분한다. 긴 기준의 모바일 줄바꿈을 확인한다. |
| UX | 평가계획 확인, 평가 연결, 명단 확인, 빈 성적 정정은 서로 다른 판단이다. | 별도 화면으로 분리한다. 평가 연결과 누락 정정은 한 항목씩 진행한다. 이전 단계 이동 시 입력을 유지하고 앞 자료 변경 시 뒤 확인·결과를 무효화한다. |
| UI | 비활성 사유·진행 상태·오류 복구가 중요하다. | 버튼 옆에 다음 단계 진입을 막는 이유를 표시하고 오류 뒤 입력을 보존한다. 드롭다운, 키보드 포커스, 390px·200%·전체 캡처를 검증한다. |

## 구현 범위

- 기존 관리자 미리보기 공개 범위를 유지한다. 새 API도 검증된 동일 관리자 계정만 허용한다.
- PDF 평가계획, XLSX·CSV·PDF 성적 파일을 지원한다. HWP/HWPX와 구형 XLS는 화면에서 PDF 또는 XLSX 변환을 안내한다.
- 원본·초안은 현재 탭 메모리에 보관한다. 새로고침·탭 종료 후 복원이나 서버 백업으로 안내하지 않는다.
- 서버는 파일 분석·학생 식별자를 제외한 평어 생성만 수행한다. 새 DB 저장·운영 배포는 이번 요청에 포함하지 않는다.
- 사실성 프롬프트는 정확성 보증이 아니다. 생성 문장과 입력 근거를 함께 검토하고 교사가 확정한다.

## 구현 후

### 1차 구현 평가와 2차 수정

같은 AI가 아래 여섯 관점을 각각 적용한 모의 검토다. 실제 전문가 여섯 명, 교사 인터뷰, 학생 사용성 시험을 실시한 것이 아니다. 모든 명단·성적·PDF 캡처는 가상 자료다.

| 독립 검토 관점 | 1차 판정·근거 | 수정 요구와 반영 | 2차 판정·남은 위험 |
| --- | --- | --- | --- |
| 웹디자인: 정보 위계 | 조건부 통과. 현재 단계·원본·대표 버튼은 구분되나 평가기준 수정 칸이 처음부터 많았다. | 기준은 읽기 형태로 먼저 보여 주고 수정 입력은 `잘못 읽힌 내용 수정` 아래로 접었다. 원본은 별도 영역에 유지했다. | 통과. 한 평가의 수준별 기준과 출처를 대조할 수 있다. 실제 PDF 표가 빽빽하면 원본 파일을 열어 확대해야 한다. |
| 웹디자인: 화면 밀도 | 수정 필요. 결과의 고정 높이 입력칸과 큰 세로 PDF가 지나친 빈 공간을 만들었다. 고정 표 열은 200% 확대에서 이름·성적 선택을 잘랐다. | 결과 입력칸은 내용에 따라 4~12행, PDF는 비율 유지·640px 최대 높이, 성적은 줄바꿈 가능한 학생별 목록으로 변경했다. | 통과. 0명·3명·30명·60명 전체 캡처에서 입력 영역과 빈 공간을 확인했다. 60명 전수 표시는 세로로 길지만 내부 스크롤로 숨기지 않는다. |
| UX: 학생 사용 흐름 | 직접 적용 대상 아님. 이 기능은 교사가 학생 자료를 처리하는 비공개 화면이며 학생에게 단계 수행을 요구하지 않는다. | 학생 이름만으로 합치지 않고 번호·행 ID로 구분했다. 학생별 평어 검토는 드롭다운으로 이동하며 완료 전 내보내기를 막았다. | 교사 흐름 기준 통과. 동명이인·빈칸·부분 실패·이전 단계·로그아웃을 모의 검증했다. 학생용 공개 화면은 만들지 않았다. |
| UX: 교실 전자칠판 흐름 | 조건부 통과. 한 번에 한 평가만 보여 주나, 모바일 결과 화면에서 다음 학생으로 바뀌어도 아래에 머물 수 있었다. | 단계·항목·검토 학생 변경 시 제목에 포커스를 두고 화면 위로 이동한다. 학생 변경 직후 제목의 화면 내 위치와 포커스를 E2E로 확인했다. | 조건부 통과. 200% CSS 확대에서 조작 가능하다. 실제 전자칠판 하드웨어 시험은 하지 않았고 개인 성적 화면의 학급 공개를 전제로 하지 않는다. |
| UI: 접근성 | 수정 필요. 초기 자동 검사에서 비활성 버튼 대비와 원본 제목의 heading 순서 오류가 있었다. | 기존 테마와 맞는 비활성 색상, 원본 h2, 접근 가능한 입력 이름·44px 조작 크기·오류 안내를 적용했다. 화면 전환 포커스를 검증했다. | 통과. 대표 화면의 main 영역 Axe 위반 0건과 포커스 검사 통과. 모든 보조기기·운영체제 조합을 검증한 것은 아니다. |
| UI: 반응형·상태 표현 | 수정 필요. `scrollWidth` 검사만으로는 상위 overflow에 가려진 200% 입력칸을 잡지 못했다. | 고정 열을 없애고 실제 입력칸 경계도 검사했다. 빈칸은 `확인 필요`와 색을 함께 표시하고, 미검토·일부 완료·전체 완료를 구분했다. | 통과. 1366px·390px·683px에서 200% CSS 확대의 전체 캡처를 재검토했다. 완료 뒤 문구 변경 시 내보내기가 다시 잠기는 동작도 통과했다. |

세 프로파일의 최종 판단: 웹디자인은 현재 과업과 원본의 역할·빈 공간 균형이 적절하고, UX는 업로드·연결·성적·생성을 분리해 복구 가능한 흐름이며, UI는 이름·빈칸·비활성·완료 상태와 좁은 화면의 조작 영역을 구분한다. 남은 공통 위험은 실제 나이스 출력 양식의 다양성, AI 인식 및 의미상 사실성, 교사의 실제 업무 시간이며 모의 검사로 해소됐다고 보지 않는다.

브라우저 검사는 Chrome·로컬 데모 서버이며 Supabase 로그인과 AI 응답을 가로챈 모의 검사다. PDF 렌더링과 CSV/XLSX 파싱·다운로드는 실제 브라우저 코드로 수행했지만 실제 OpenAI나 운영 Supabase를 호출하지 않았다. 서버 단위 검사는 인증 스푸핑·익명/일반 계정 거절, PDF 검사 전 비용 호출 금지, 사용량 검사 실패 시 중단, 변조된 근거·누락 결과 거부를 포함한다. 최초 샌드박스 안에서 마지막 포커스 E2E 서버 대기가 끝나지 않아 해당 실행은 중단했고, 자동 승인된 로컬 Chrome 실행 환경에서 재검사했다.

### 반영 상태와 제한

아래는 1차 로컬 개발 완료 당시 상태다. 이후 사용자 요청으로 수행한 배포·실제 AI 검증 결과는 [운영 검증 기록](production-verification.md)을 따른다.

- 로컬 소스 구현만 완료. GitHub push·PR·main 병합·프런트엔드 배포·`neis-helper` 함수 배포는 하지 않았다. 새 DB 마이그레이션은 없다.
- 기존 관리자 미리보기 범위를 유지했다. 나머지 세 기록 기능은 비활성이다.
- 실제 평가계획/나이스 파일의 AI 인식 정확도와 생성 품질, 운영 로그인·사용량 RPC·실제 비용·응답 시간은 미검증이다. 근거 ID와 인용 일치가 의미상 사실성 검증을 대신하지 않는다.
- 평가계획 전체가 인식됐는지는 교사가 원본과 대조해야 한다. XLSX/CSV는 번호·이름이 같은 제목 행에 있어야 하고 비표준 병합 머리글은 다시 저장해야 할 수 있다. 4단계 성적은 임의 변환하지 않는다.
- 새로고침·탭 종료를 넘는 초안 저장, 나이스 자동 입력, HWP 직접 분석, 실제 학생 대상 시험, 운영 인증을 사용한 포터블 검증은 범위 밖이다.
- 외부 작업일지 `../schooldoc-docs/development-history.md`는 이 체크아웃에 없어 수정하지 않았다. 관련 구현·검증·남은 작업은 이 문서와 DEVELOPMENT.md에 기록했다.
