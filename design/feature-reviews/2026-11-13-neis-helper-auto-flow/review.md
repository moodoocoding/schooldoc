# Neis Helper 교과 평어 흐름 재구성 검토

AI의 모의 검토이며 실제 전문가·교사 인터뷰나 승인 결과가 아니다.

## 요청과 범위

- 평가계획 입력을 두 방식으로 나눈다.
  1. 교과를 먼저 고르고 그 교과의 평가계획 파일을 넣는다.
  2. 평가계획 전체를 넣으면 AI가 교과별로 나누고 교사는 교과만 고른다.
- 파일을 넣은 뒤 단계마다 확인 버튼을 누르게 하지 않는다. 자동으로 정리하고 결과와 확인이 필요한 항목만 보여 준다.
- 성적이 비었거나 읽지 못한 학생은 평어를 만들지 않고 결과 표에 `성적 확인 필요`로 표시한다(사용자 결정).
- 서버 함수·DB는 바꾸지 않는다. 교과 필터와 자동 연결은 브라우저에서 처리한다.

## 기존 흐름의 문제

12단계 중 평가(항목 수만큼)·성적 열(열 수만큼)·평가별 성적(평가 수만큼)·학생별 검토(학생 수만큼)를 버튼으로 하나씩 넘긴다.
30명·평가 4개 기준 최소 약 45번의 확인 클릭이 필요하다. 시트·제목 행도 대부분 자동 판별 가능한데 매번 선택하게 했다.

## 구현 전 세 프로파일 검토

| 관점 | 판정 | 근거·반영 방향 | 남은 위험 |
| --- | --- | --- | --- |
| 웹디자인 | 수정 필요 | 화면마다 한 항목만 크게 보여 줘 전체 상황을 알 수 없다. 3화면(평가계획 → 교과·성적 → 결과)으로 줄이고 결과를 학생 목록 한 화면에 모은다. 확인 필요 항목은 상단 요약과 행 단위 표시로 구분한다. | 30~60명 목록의 세로 길이 |
| UX | 수정 필요 | 자동으로 판단할 수 있는 시트·제목 행·열 연결을 교사에게 묻는다. 자동 처리 후 예외(빈 성적, 연결 못 한 열, 기준 누락)만 그 자리에서 고치게 한다. 전체 계획의 이점(교과를 바꿔 계속 작성)을 살린다. | 자동 연결이 틀렸을 때 교사가 놓칠 가능성 → 연결 방식(제목 일치·유사·순서)을 결과 화면에 표시 |
| UI | 수정 필요 | 방식 선택은 라디오 그룹, 교과는 라디오 그룹(개수 표시), 학생별 상태는 문자·아이콘으로 구분해 색에만 의존하지 않는다. 행 단위 버튼에 학생 번호·이름이 포함된 접근 가능한 이름을 준다. | 긴 평어 입력칸의 모바일 높이 |

## 1차 구현

- 화면을 `평가계획 → 교과·성적 → 평어 결과` 3단계로 줄였다(`NeisPlanStep`, `NeisPrepareStep`, `NeisResultsStep`, 논리는 `autoPipeline.ts`).
- 교과별 방식은 고른 교과의 평가만 남긴다. 교과 이름이 없거나 한 교과뿐인 파일은 고른 교과로 보고, 다른 교과만 여럿 있으면 임의로 바꾸지 않고 `전체 평가계획으로 보고 교과 고르기`를 안내한다.
- 전체 방식은 교과별 평가 수와 함께 교과를 고르게 하고, `다른 교과 작성`은 평가계획을 다시 분석하지 않는다.
- 성적 파일은 시트·제목 행을 자동으로 찾고, 열은 제목 일치 → 비슷한 제목 → (제목이 하나도 맞지 않고 개수가 같을 때만) 순서로 연결한다. 연결 방식은 결과 화면에 표시하고 바꿀 수 있다.
- 평가기준이 빈 평가는 평어 근거에서 빼고 결과 화면에서 입력하게 한다. 빈 성적·읽지 못한 기호·번호 문제가 있는 학생은 생성하지 않는다(추측 금지). 성적을 입력하면 그 학생만 바로 생성한다.
- 생성은 동시 3건으로 진행하고, 한도·로그인 오류에서는 나머지를 멈춘다. 학생별 `검토 완료` 버튼을 없앴다.
- 서버 함수·DB 변경 없음.

### 1차 구현의 여섯 독립 관점 모의 평가

각 행은 서로 다른 기준으로 수행한 AI 모의 평가다. 여섯 명의 실제 전문가 검토가 아니다. 근거는 E2E 전체 페이지 캡처(1366px·390px·683px/200%·30명·60명)다.

| 관점 | 판정 | 근거 | 수정 요구 |
| --- | --- | --- | --- |
| 웹디자인: 정보 위계 | 통과 | 결과 첫 화면에 현황(완성·확인 필요·사용 평가) → 저장 버튼 → 자동 정리 요약 → 학생 목록 순서. 확인 필요 학생은 배경과 `⚠ 성적 확인 필요` 문자로 구분된다. | 없음 |
| 웹디자인: 화면 밀도 | 수정 필요 | 390px에서 현황 카드 세 개가 세로로 쌓여 약 280px를 차지한다. 데스크톱에서 한 줄 평어에도 3줄 입력칸이 잡혀 빈 공간이 생긴다. | 모바일 현황을 3열로 압축, 입력칸 최소 2줄 |
| UX: 교사 작성 흐름 | 통과 | 교과별 계획 기준 확인 클릭이 `평가계획 분석`·`평어 만들기` 두 번으로 줄었다(기존 30명·평가 2개 기준 약 40번). 예외 학생은 그 행에서 성적을 고르면 바로 생성된다. | `확인 필요` 보기에서 고친 학생이 바로 사라져 결과를 볼 수 없었다 → 누른 시점의 학생을 유지(반영함) |
| UX: 교실 전자칠판 흐름 | 판단 보류 | 교사 개인 작성 도구이며 학생·전자칠판 사용 흐름이 없다. 200% 확대에서 목록·버튼이 읽히고 넘치지 않는다. | 실제 전자칠판 사용성은 미검증 |
| UI: 접근성 | 수정 필요 | 주 영역 Axe 검사에서 결과 화면의 h1 → h3 건너뜀이 발견됐다. `<label>` 안 교과 선택의 접근 가능한 이름이 "교과 선택하세요"로 계산됐다. | h2로 조정, 선택 상자에 `aria-label` 지정(반영함) |
| UI: 반응형·상태 표현 | 수정 필요 | 390px 입력칸에서 평어가 음절 단위로 줄바꿈된다("소/수"). 긴 이름이 이름 열에서 어절 중간에 끊긴다. 접힌 원본 미리보기가 평가마다 미리 렌더링되어 같은 이름의 조작이 중복됐다. | 입력칸 `break-keep`, 이름 열 10rem·`break-keep`, 펼칠 때만 미리보기 렌더링. 입력 중 기준이 채워져도 패널이 접히지 않게 함 |

## 2차 개발과 재검증

- 현황 카드를 `auto-fit` 3열로 압축했다(390px에서 한 줄). 입력칸은 `break-keep`과 내용 높이(`field-sizing: content`, 미지원 브라우저는 줄 수 추정)로 바꿨다.
- 200% 확대(683px) 캡처에서 학생 행이 화면 폭 기준 `sm:` 2열을 유지해 평어 칸이 한 글자 폭으로 무너지는 문제를 발견했다. 학생 행·열 연결 행·방식 카드를 실제 남은 폭으로 줄바꿈하는 flex/`auto-fit` 배치로 바꿨다.
- `근거 보기`를 글자 수·다시 생성과 같은 줄의 토글 버튼(`aria-expanded`)으로 옮겨 행 높이를 줄였다. 60명 데스크톱 전체 페이지 높이가 14,225px → 9,269px로 줄었다.
- `accessibleNamesDoNotOverlap` 단위 검사가 `교과` ⊂ `교과 이름`을 잡아 `과목명 직접 입력`으로 바꿨다. 학생 행 버튼 이름도 `N번 이름 다시 생성`으로 바꿔 `N번 이름 평어`와 겹치지 않게 했다.
- 재확인 캡처: 1366px·390px 결과(확인 필요/완료), 683px/200% 30명, 1366px 60명, 전체 계획 교과 선택, PDF 성적 원본, HWP·HWPX 변환 지면. 가로 넘침·잘린 조작 없음, 주 영역 Axe 위반 0건(각 캡처 시점).

| 관점 | 판정 | 근거 | 남은 위험 |
| --- | --- | --- | --- |
| 웹디자인 | 통과 | 결과 화면 첫 화면에 현황·저장·예외가 모이고, 완성/확인 필요가 배경·아이콘·문자로 구분된다. 모바일·확대에서 열 균형이 무너지지 않는다. | 실제 평어(200~400자)는 가상 문장보다 길어 행 높이가 커진다 |

| UI | 통과 | 라디오·토글·행 버튼의 접근 가능한 이름이 겹치지 않고, 상태가 색에만 의존하지 않는다. Axe·키보드 파일 선택 E2E 통과. | 화면낭독기 실기기 확인은 하지 않았다 |

## 검사 결과와 한계

- `npm run typecheck` 통과, `npm run lint` 통과(Neis 관련 경고 없음).
- `npm test`: 83개 파일, 676건 통과(새 `tests/unit/neisAutoPipeline.test.ts` 포함).
- `PLAYWRIGHT_TEST_PORT=5291 CI=1 npx playwright test tests/e2e/neis-subject.spec.ts`: 15건 통과. 같은 설정으로 `admin-tool-visibility`·`app-shell-scroll` 포함 56건 통과(라벨 변경 전 실행, 이후 Neis 15건 재실행 통과). 기본 4173 포트는 다른 워크트리의 E2E가 사용 중이라 다른 포트를 썼다.
- E2E는 로컬 데모 서버·모의 인증·AI 대체 응답이다. 실제 OpenAI·Supabase·실제 나이스 양식으로 새 흐름을 확인하지 않았다. 서버·DB 변경은 없다. 커밋·push·배포는 하지 않았다.
