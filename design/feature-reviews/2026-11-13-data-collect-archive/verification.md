# 자료 수합 보관함·재개·삭제 검증

2026-11-13, 별도 워크트리의 `codex/fix-data-collect-db-io`에서 진행했다. 첨부 화면은 기본 목록에 수합 중과 기한 마감·종료 카드가 함께 나오는 문제를 확인하는 데만 사용했다. 검증 자료와 화면 캡처에는 가상 제목·이름·파일만 사용했다.

## 동작과 데이터 경계

- 기본 목록은 `수합 중`, 기한 만료·직접 종료 목록은 `보관함`이다. DB가 소유자와 상태 범위를 먼저 적용한 뒤 최대 21개(표시 20개 및 다음 페이지 확인용 1개)를 조회한다. 마감 경계에서는 화면의 시각으로 기본 목록에서 항목을 빼고, 보관함을 열면 별도 범위로 조회한다. 시계가 DB를 주기적으로 읽지 않는다.
- 현황의 `다시 열기`에서 미래의 마감 시각 또는 기한 없음을 선택한다. 상태와 기한을 한 SQL 트랜잭션에서 변경하며 공개 토큰, 명단, 기존 회신·파일, 재제출 설정과 보관 기간은 유지한다.
- `영구 삭제`는 로그인한 소유자가 보관된 대상의 제목·제출 대상·회신 이력·실제 저장 파일 수량을 검토하고 동의한 경우에만 시작한다. 최근 발급한 업로드의 재사용을 막기 위해 운영에서는 종료·마감 시점(생성이 더 늦으면 생성 시점)부터 2시간 15분 대기한다. 이는 [Supabase 서명 업로드 유효 기간](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl)과 진행 중인 요청 여유를 고려한 앱의 기준이다.
- 잠금 안에서 수합 상태·변경 시각·수량을 재확인한 다음 진행 기록을 남긴다. Storage API는 소유자의 배포 경로와 해당 수합의 제출 경로만 최대 100개씩 처리한다. 한 요청에 최대 1,000개이며, 실패 또는 남은 파일이 있으면 DB 기록을 유지하고 다시 확인해 이어간다. 파일을 다 지우기 전에는 다시 열 수 없다. Storage 메타데이터는 읽기만 하고 빈 경로를 확인한 뒤 수합 DB 행과 관련 기록을 정리하며, 감사 기록에는 제목·파일명·명단을 남기지 않는다.
- 설정의 파기 예정 자료에서도 자료 수합은 같은 현황 확인 흐름으로 연결한다. 가정통신문·학급 미션의 기존 동작과 보관 기준은 유지한다.

## 검증 경계와 배포

- 실제 설치 Chrome 157.0.8103.40, localhost:4183 데모 앱: 자료 수합 E2E 18개 통과. 창을 연 보관함 재개·삭제 검사도 별도로 통과했다. 실제 마감 시각을 기다려 기본 목록에서 추가 조회 없이 사라지고 보관함에 나타나는 것을 확인했다.
- 환경 설정 E2E 7개 통과. 파기 예정 자료 수합에서 현황의 수량 확인으로 연결되고 취소하면 자료가 남는다. 기존 가정통신문 파기도 확인했다. 첫 실행에서는 기존 테스트가 데모 안내와 파기 성공 알림을 함께 선택해 실패했고, 성공 문구를 포함한 상태 요소로 검사 대상을 좁혀 재통과했다.
- `npm test` 59파일·479개, `npm run typecheck`, `npm run lint`, `npm run build` 통과. 기존 린트 경고 7개와 큰 번들 경고는 유지한다. Deno에서 관리·공개 함수 타입을 확인했다.
- 실제 별도 PostgreSQL 18.6: `node tests/integration/dataCollectPostgres.local.mjs`에서 마이그레이션 5개와 동작 검사 23개 통과. 소유자/RLS, 마감 후 재개, 파일 일부 실패, 중복 마무리, 재개와 삭제의 경합을 검사했다. Storage 메타데이터 테이블은 시험용 fixture다.
- 실제 관리 Edge Function의 로컬 HTTP 계약 검사는 Auth·PostgREST·Storage를 모의 응답으로 구성했다. 확인 없는 삭제 요청 거부, Storage 오류 시 DB 마무리 미호출, 재시도에서 파일 제거 후 마무리 호출을 확인했다.
- 전체 화면·결과 JSON은 이 워크트리의 로컬 `test-results/data-collect-archive-evidence/`에 저장했다. 이전 10월 검증 증거는 덮어쓰지 않았다.
- 실제 원격 Supabase의 로그인·Storage/DB 연동은 미실행이다. 가상 자료 외 삭제는 하지 않았다. 새 마이그레이션 `202611130400_data_collect_archive.sql`의 로컬 번호 중복은 없었으며 원격 이력은 미비교다. 원격 반영이 요청되면 이력 확인 → 마이그레이션 → `data-collect-admin` → 프런트엔드 순으로 적용한다. 공개 함수 코드는 바꾸지 않았다.
- 검증 시점에는 코드와 문서를 자료 수합 워크트리에만 수정했다. 이후 GitHub 브랜치 반영 범위는 [작업 일지](../../../docs/feature-review-data-collect-2026-10-01.md)를 참조한다. main 병합·DB·Edge Function·프런트엔드 운영 배포는 미실행이다.
