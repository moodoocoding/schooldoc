## 바뀐 동작

목록은 예약 내용 전체 대신 20개 요약을 읽고, 예약표는 선택한 실·월~토 한 주의 최대 54개 예약을 읽는다. 진행 업무의 정상 요약 RPC는 유지하고 특별실 fallback만 요약 조회로 바꿨다. 휴관 목록은 20개씩 읽고 설정 축소·휴관·삭제의 영향 수는 필요한 순간 서버에서 집계한다.

공개 저장은 한 RPC 안에서 요청 제한, 공개 토큰·비밀번호, 현재 상태·운영 범위·휴관, 기대 예약 ID/버전을 확인한다. 9교시를 허용하며 빈 칸 동시 생성·오래된 수정은 409로 거절한다. 충돌 시 현재 내용과 내 초안을 보여 주고 명시적으로 재확인한다. 저장 결과로 해당 셀을 반영하므로 정상 저장 뒤 전체 표를 다시 읽지 않는다. 반복 예약은 실제 INSERT RETURNING 결과를 안내하고 동일 작업 재시도의 결과를 보존한다.

공개 알림 전용 JWT와 private Broadcast 채널을 구현했다. 운영 정보 채널과 선택 실/주 채널만 구독하며 연속 버전의 셀 변경은 직접 반영한다. 누락·재연결·복귀는 조건부 스냅샷으로 복구하고 숨긴 탭은 조회를 멈춘다. 공개 토큰·비밀번호·권한 세대가 바뀌면 캐시와 초안을 폐기한다. 공개 JWT는 메모리에만 두며 예약 테이블 직접 조회나 알림 발행 권한을 주지 않는다.

조회 실패를 빈 표로 바꾸지 않고 재시도를 제공한다. 늦은 이전 범위의 응답은 현재 표를 덮지 않는다. 실패한 초안은 탭 메모리에서 보존한다. 관리 폼은 수정하지 않은 필드만 외부 변경과 병합하며 충돌 필드는 재확인을 요구한다. 영향 수 조회 실패는 저장을 막고 재시도를 제공한다. NEIS는 검증된 결과의 차이만 원자적으로 적용하며 같은 결과는 행사 DML·알림을 생략한다.

한국 날짜·일요일의 다음 주 선택, 토요일·연도 경계를 공통 규칙으로 처리한다. 50실은 선택 상자로 탐색하고 날짜로 직접 이동한다. 모바일 표는 두 줄 라벨, 낮은 화면과 200% 확대의 입력창은 내부 스크롤을 사용한다. 종료한 예약의 상세도 읽을 수 있다. 공개·관리 모두 선택 실의 주간표를 A4 가로로 인쇄한다.

## DB 계측

[SQL 계측 도구](measure-sql.ts)가 실제 PGlite PostgreSQL 엔진에 네 개의 마이그레이션을 적용했다. 1/3/50실마다 52주 이력과 최대 주간 자료를 만들고 내부 조회 SQL에 EXPLAIN (ANALYZE, BUFFERS)를 실행했다. [전체 결과](implementation-evidence/sql-measurements.json)에 실행계획·블록·시간·논리 DML을 보존했다.

| 실 수 | 기존 공개 주간 예약 반환 | 새 선택 실 주간 예약 반환 | 기존 교사 전체 예약 이력 | 기존 예약 projection 바이트 | 새 전체 snapshot 바이트 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 54 | 54 | 105 | 11,827 | 12,226 |
| 3 | 162 | 54 | 315 | 35,479 | 12,428 |
| 50 | 2,700 | 54 | 5,250 | 591,301 | 17,256 |

바이트의 기존 값에는 운영 메타 응답이 빠져 있고 새 값에는 메타가 포함되므로 완전히 같은 HTTP 응답의 절감률로 해석하지 않는다. 로컬 캐시 읽기에서 physical read는 0이었다. 작은 1/3실에서는 새 내부 SQL의 shared hit가 기존 예약 조회 하나보다 많았고, 50실에서는 읽기 범위·블록이 줄었다. 운영 디스크 IOPS·요금·WAL 감소율은 측정하지 않았다.

논리 DML 계측: 단일 저장은 예약 1 + 실/주 상태 1 + 시험용 메시지 1 + 요청 제한 1행이며 부모 예약표 UPDATE는 0이다. 동일 단일 작업 응답 재시도와 동일 값 저장은 요청 제한만 1회 갱신한다. 52주 반복은 예약 52 + 상태 52 + 메시지 52 + 반복 결과 1 + 요청 제한 1행이다. 같은 반복 작업 재시도는 요청 제한만 갱신하고 생성 52건 결과를 유지했다. 시험용 감사 트리거의 쓰기는 이 집계에서 제외했다. 실제 Supabase Broadcast의 WAL·정리 비용은 별도다. 요청 제한 테이블의 dead tuples·만료 키 비용도 운영 계측이 남아 있다.

25개 예약표 요약은 첫 페이지 20/다음 5개, 중복 0개, 상세 예약 라벨 0개 반환을 확인했다. 반복 결과는 만료 1일이며 오래된 로그를 해당 예약표의 반복 요청에서 정리한다. 취소 응답 유실 후 재시도는 이미 빈 상태를 충돌로 안내할 수 있다. 삭제 후 새로 생긴 다른 예약을 지우지 않으며 모든 단일 변경에 영구 작업 로그를 추가하지 않았다.

## 실제 Chrome 검증 범위

설치된 Google Chrome을 Playwright의 `channel: chrome`과 agent-browser로 실제 실행하고 버튼·입력·키보드를 제어했다. headed Chrome에서도 공개 예약을 입력·저장하고 실제 로컬 SQL 행을 확인했다. 가상 학교·자료만 사용했으며 운영 계정·개인정보를 사용하지 않았다.

- 데모 4194: localStorage 기반 제품 흐름. 특별실 60개 + 진행 업무 4개 통과. 스크롤 18개와 1인 1역 인쇄 1개도 통과했다. [데모 결과](implementation-evidence/demo-chrome.txt), [스크롤 결과](implementation-evidence/final-smoke.txt), [인쇄 회귀](implementation-evidence/other-print.txt).
- SQL 4195→4196: 비데모 저장소→실제 HTTP 처리기→실제 PGlite SQL RPC. 응답 모킹 없이 9교시·동시 충돌·조회/저장 503 복구·지연 주간 응답·반복 경쟁의 5개 Chrome E2E 통과. [결과](implementation-evidence/sql-chrome.txt), [headed DB 증거](implementation-evidence/headed-sql-metrics.json), [전체 화면](implementation-evidence/11-headed-chrome-sql.png).
- 관리 오류 복구: 실제 제품 컴포넌트에 실패 콜백을 주입하는 Chrome 검사 1개와 관련 관리/휴관/운영 회귀를 실행했다. SQL 또는 원격 인증 검사로 간주하지 않는다. [하네스](admin-recovery-harness.jsx), [검사](../../../tests/e2e/special-rooms-admin-recovery.spec.ts), [결과](implementation-evidence/admin-final-chrome.txt).
- [전체 화면 검증 도구](validate-implementation.mjs): 50실·54셀, 작은 화면·CSS 200%, 두 관리 탭, 한국 날짜, 키보드 탭, 1920×1080 전자칠판 크기, 종료 상세, QR PNG 저장·PDF를 실제 Chrome에서 확인했다. [측정](implementation-evidence/visual-chrome.json)에 공개·관리 axe 위반 0, pageerror 0을 기록했다.
- 출력: [공개 A4](implementation-evidence/public-a4.pdf)와 [관리 A4](implementation-evidence/teacher-a4.pdf)는 각각 1장, [긴 자료](implementation-evidence/boundary-a4.pdf)는 2장이다. 모든 페이지를 Poppler로 렌더해 표·여백·줄바꿈·페이지 경계를 직접 확인했다. 54개 예약 식별자가 모두 남고 페이지 바깥 텍스트 bbox는 0이다. [페이지 검사](implementation-evidence/pdf-inspection.json). 다른 기능인 1인 1역은 A4 세로 1장 유지.

PGlite는 실제 SQL 엔진이지만 단일 프로세스여서 PostgreSQL 다중 연결 잠금 시험을 대신하지 않는다. `crypt/gen_salt`와 `realtime.send`는 명시한 SQL 시험 adapter를 사용했고 실제 bcrypt·Supabase Auth·Realtime 전송을 검증하지 않았다. 기존 첫 마이그레이션의 publication 등록만 시험 환경에서 제외했으며 새 마이그레이션 SQL은 그대로 실행했다. HTTP 실패는 시험 서버의 503 제어로 재현했다. 실제 NEIS·운영 비밀번호·원격 RLS/Realtime 서비스·50탭/100변경 부하·물리 프린터·교실 장비·실제 교사 사용성 시험은 미실행이다.

## 적용 전 경계와 설계 차이

- 알림 서명키가 없거나 발급에 실패하면 조회·저장은 계속 가능하며 수동/복귀/5분 조건부 확인으로 작동한다. 실제 빠른 갱신은 Supabase가 알림 전용 JWT를 신뢰하고 private 권한 검사를 통과하는 것을 시험 환경에서 확인한 뒤 활성화한다. 키 설정은 [개발 참고](../../../DEVELOPMENT.md)의 특별실 절을 따른다.
- 초기 스냅샷과 채널 구독 사이 유실을 막기 위해 구독 성공 직후 조건부 확인 1회를 추가했다. 따라서 알림이 연결된 최초 진입은 계획의 절대 1회 목표와 달리 bootstrap + 확인 2회가 될 수 있다. 정상 셀 변경과 내 저장 성공 뒤 조회 0회는 유지한다.
- 교사 머리글의 모든 실 ‘이번 주 예약 수’는 선택 실의 변경을 즉시 반영한다. 다른 실의 변경 수량은 수동/복귀/5분 확인 때 갱신한다. 모든 실 상세 채널을 구독하거나 부모 전역 카운터를 매번 쓰지 않았다. 마지막 확인 시각을 제공한다.
- 구버전 `metadata/week` 읽기 응답을 유지했다. 이 경로는 모든 휴관/실의 해당 주를 읽을 수 있어 새 경로와 같은 조회 상한이 아니다. 구버전 저장은 기대 버전/작업 ID가 없으면 갱신 요구 오류로 차단한다. 서버 먼저 적용하고 새 프런트엔드를 배포한 후 구버전 읽기 사용량을 확인해 호환 경로를 제거한다.
- 자동 승인 검토가 처음의 광역 restrictive Realtime 정책을 다른 기능 영향 때문에 거절했다. 실행하지 않고 `sr:` 행에만 적용하는 가드로 좁혔으며, 기존 다른 기능 허용 정책을 함께 둔 실제 SQL truth table로 타 기능 유지·타 특별실 차단을 확인한 뒤 로컬 파일 변경이 승인됐다. 원격 정책 변경은 하지 않았다.
- 마이그레이션은 새 `202610010600_special_room_scoped_sync.sql` 하나로 추가했다. 다른 브랜치/작업트리 번호 중복을 확인했다. 원격 `migration list --linked`와 기존 Realtime 정책·JWT 신뢰·다중 연결 잠금·물리 I/O/부하 검증 후 secrets → DB → 지정 함수 → 프런트 순서로 적용해야 한다. 기존 키·암호화·개인정보 보관 정책은 변경하지 않았다.
- 외부 공유 작업일지와 `pro/ux-ui-expert.md`는 이 checkout에 없어 읽었다고 보고하지 않는다. 기존 기능별 [개발일지](../../../docs/feature-review-special-rooms-2026-10-01.md)에 새 `(codex)` 항목을 추가했다.
