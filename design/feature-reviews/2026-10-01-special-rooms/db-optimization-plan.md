# 특별실 예약 DB 최적화 설계계획

- 작성일: 2026-10-01. [기능 수정계획](fix-plan.md)을 Supabase I/O 관점에서 보완한 설계 기준이다.
- 사용자 선택: **빠른 갱신 우선, 변경 알림 기반 동기화까지 설계**.
- Supabase와 기존 공유 수정 정책을 유지한다. 현재는 문서만 작성하며 DB 설정·키·마이그레이션·제품 코드를 변경하지 않는다.
- 성능 수치는 현재 소스의 호출 구조 분석과 가정에 따른 계산이다. 운영 프로젝트의 실제 디스크 IOPS·WAL·요금은 측정하지 않았다.

## 무엇을 줄일 것인가

API 호출 횟수, SQL 실행/읽는 행·블록, 네트워크 전송량, 물리 디스크 I/O, 쓰기/WAL은 서로 다른 지표다. RPC 하나 안에서 넓은 조회를 여러 번 실행하면 디스크 부담은 그대로일 수 있다. 반대로 작은 범위의 반복 조회는 메모리 캐시에 적중할 수 있어 API 1회가 디스크 I/O 1회라는 계산은 성립하지 않는다. [Supabase 디스크 지표](https://supabase.com/docs/guides/platform/compute-and-disk), [PostgreSQL 실행계획/버퍼](https://www.postgresql.org/docs/current/using-explain.html)를 구분하여 측정한다.

이 설계는 **반복 전체 조회 제거 → 필요한 행만 조회 → 저장 결과 재사용 → 쓰기를 늘리는 최적화는 측정 후 도입** 순서다. 예약의 동시성·권한·오류 복구를 줄여서 성능을 얻지는 않는다.

## 현재 코드에서 확인한 부담

| 경로 | 현재 동작 | 설계 변경 |
| --- | --- | --- |
| 교사 목록 | [listRemoteBoards/assemble](../../../src/features/specialRooms/specialRoomsRepository.ts)가 예약표와 실·예약·학사일정·휴관 자료를 기간 없이 조립 | 페이지별 예약표 요약과 수량만 반환 |
| 진행 업무 | 정상은 [기존 요약 RPC](../../../src/features/activeWork/activeWorkRepository.ts) 1회. 실패/미적용 때 [specialRoomsProvider](../../../src/features/activeWork/activeWorkProviders.ts)가 전체 조립으로 복구 | 정상 요약 유지, 복구 경로의 특별실 부분도 경량화 |
| 교사 관리 | [getRemoteBoard](../../../src/features/specialRooms/specialRoomsRepository.ts)가 모든 기간을 읽고 화면에서 현재 주만 필터 | 선택 실·주 예약 + 필요한 메타/요약 분리 |
| 공개 초기 | metadata와 week를 별도로 호출해 예약표 확인과 요청 제한 처리를 중복 | 공개 bootstrap 1회, 비밀번호 해제 성공 응답에 첫 주 자료 포함 |
| 공개 저장 | [run/refreshWeek](../../../src/features/specialRooms/PublicSpecialRoomsPage.tsx)가 쓰기 성공 후 주간 재조회 | 확정된 한 셀의 반환값으로 캐시 갱신 |
| 구독 | [subscribeRemoteSpecialRooms](../../../src/features/specialRooms/specialRoomsRepository.ts)가 예약 테이블 전역 이벤트로 전체 load를 유발 | 권한 있는 실/주 채널에 셀 변경을 전달, 누락/재연결 때만 범위 재조회 |
| 조회 제한 | [consumeRateLimit](../../../supabase/functions/special-rooms-public/index.ts)와 [SQL](../../../supabase/migrations/202608210002_special_room_reservation.sql)의 UPSERT가 조회 때도 카운터를 씀 | 제한은 유지하되 불필요한 요청 자체를 줄임 |
| 학사일정 | [관리 함수](../../../supabase/functions/special-rooms-admin/index.ts)가 기간 삭제 후 전부 upsert | 트랜잭션에서 변경된 행사만 삽입/수정/삭제 |

정상·비밀번호 없는 경로의 소스 기준: 공개 첫 화면은 Edge 요청 2회, Edge→DB API 왕복 9회(metadata 5회 + week 4회)다. 단일 예약은 쓰기 6회와 정상 후속 week 4회로 DB 왕복 10회다. 비밀번호 검증·경쟁 재시도·중복 이벤트가 있으면 증가한다. 이는 SQL 내부 문장 수나 실제 디스크 I/O 횟수가 아니다.

교사 목록·상세의 기본 조립은 DB API 5회다. 기간 제한이 없다는 것은 소스에서 확인했으며, 원격 API의 최대 반환 행 설정은 확인하지 않았다. 따라서 모든 이력이 반드시 전송된다고 단정하지 않는다. 요약 수량은 반환 행 제한에 잘려 틀어지지 않도록 서버 집계로 검증한다.

## 1. 조회 모델을 화면의 필요에 맞게 분리

### 교사 목록·진행 업무

새 SpecialRoomBoardSummary 모델에 id·title·status·updatedAt·roomCount·bookingCount만 둔다. 첫 목록은 20개를 기본으로 하고 안정적인 updatedAt+id 순서로 다음 페이지를 읽는다.

진행 업무는 이미 [activeWorkService](../../../src/features/activeWork/activeWorkService.ts)의 정상 요약 경로와 [SQL 집계](../../../supabase/migrations/202608270001_active_work_summary.sql)를 갖는다. 원격 적용 여부는 미확인이다. 기존의 열린 예약표·수량 의미를 유지하고 집계 규칙을 재사용한다. RPC 실패 복구에 호출되는 특별실 공급자만 신규 요약 모델로 바꾸며 다른 기능의 공급자를 일괄 재작성하지 않는다. 페이징을 적용하는 복구에서도 열린 항목을 빠뜨리지 않는다.

- 예약 라벨·전체 학사일정·휴관·비밀번호 해시는 목록 응답에서 제외한다.
- 하나의 요약 RPC에서 로그인한 소유자만 대상으로 선택된 예약표의 수량을 집계한다. COUNT도 관련 인덱스/행을 읽을 수 있으므로 무료 조회로 취급하지 않는다.
- 요약의 진행 중 요청과 짧은 메모리 캐시는 동일 사용자·조건일 때만 공유한다. 기존 전체 도구 요약 RPC와 특정 예약표 페이지를 같은 결과로 오인하지 않는다. 로그아웃/계정 전환 시 즉시 비운다.
- 예약 1건마다 전체 목록을 다시 읽지 않는다. 현지 작업 결과나 알림으로 해당 요약만 갱신/무효화한다.
- 삭제 확인을 열 때 최신 대상·수량을 조회한다. 확인 이후 수량이 바뀌면 서버가 다시 확인하게 하며, 실제 삭제는 교사의 기존 확인 절차를 유지한다.
- 수량 캐시 테이블/예약표별 누적 카운터는 초기안에 넣지 않는다. 예약마다 추가 쓰기를 만드는 대신 집계 비용을 먼저 측정한다.

### 공개·관리 예약표

예약 조회 범위는 **예약표 + 선택한 실 + 월요일~토요일**로 제한한다. 현재 유니크 제약상 한 실의 주간 예약은 최대 54칸이다. 숨겨진 교시/토요일 기록은 삭제하지 않고 운영 설정에 맞춰 화면에서 표현한다.

- 최초 bootstrap은 기본 실을 서버에서 고르고 메타와 해당 주를 한 응답으로 반환한다. 보호된 판은 잠금 정보를 반환하고 예약은 읽지 않는다. 해제 성공 시 첫 snapshot도 함께 돌려 unlock 뒤 별도 week 요청을 없앤다.
- 주/실 이동은 해당 범위만 읽는다. 메타는 알려진 metadataRevision/calendarRevision과 달라졌을 때 갱신한다.
- 공개 요청의 제한 카운터·예약표/비밀번호 확인·snapshot을 하나의 DB API RPC로 묶되 내부 SQL 비용을 계측한다. 카운터 처리 뒤 자료 조회는 같은 SQL 스냅샷을 사용하며 읽기용 SELECT에 불필요한 행 잠금을 걸지 않는다.
- 결합 RPC에서 사업 오류를 단순 예외로 올려 제한 카운터까지 롤백하지 않게 한다. 충돌/비밀번호 오류/제한 초과는 상태 응답으로 반환하고 Edge에서 HTTP 코드로 변환하는 등 제한 기록을 보존한다. 자료 쓰기 실패는 별도 하위 트랜잭션으로 롤백하고 전체 실패 시에는 차단한다.
- 학사일정은 해당 주, 공개 휴관은 해당 실 또는 전체 실이며 해당 주와 겹치는 기간만 읽는다. 학기말 계산은 필요할 때 한정한 미래 기간에서 수행한다.
- 관리 화면의 주간 전체 예약 수는 별도 집계로 기존 의미를 유지한다. 실별 상세 라벨을 전부 내려보내 전체 수량을 계산하지 않는다.
- 운영 교시 축소/토요일 제외의 영향 수는 설정 변경 때, 휴관 영향 수는 유효한 기간/실 선택 때만 소유자 집계 RPC로 구한다. 입력 중 디바운스·동일 조건 캐시·이전 요청 무시를 적용한다.
- 초기 관리 휴관 목록은 페이지별로 읽고 필요한 이전 항목을 이어 읽는다. 표에 적용할 주간 휴관과 관리 목록을 구분한다.

[기존 인덱스](../../../supabase/migrations/202608210002_special_room_reservation.sql)의 unique(room_id, booking_date, period)는 선택 실·날짜 조회에, (board_id, booking_date)는 주간 집계에 재사용한다. (board_id, day), unique(board_id, position), 소유자 인덱스도 먼저 활용한다. 인덱스 추가는 EXPLAIN/실측 후 결정한다.

## 2. 빠른 동기화는 작은 변경 알림으로

### 권한과 채널

전체 테이블 Postgres Changes 구독을 기본 동기화 경로에서 빼고 **예약표 메타 + 선택한 실/주 private Broadcast**로 바꾼다. Postgres Changes는 구독자별 이벤트 권한 검사 비용이 생긴다. [공식 확장성 설명](https://supabase.com/docs/guides/realtime/postgres-changes#scaling-postgres-changes).

- 교사는 기존 인증으로 소유한 예약표의 메타와 선택 실/주 채널만 받는다. 목록/진행 업무에는 소유자별 요약 변경 채널을 사용하며 바뀐 예약표의 요약만 무효화한다.
- 공개 사용자는 토큰·필요한 비밀번호 확인 후 해당 예약표 채널을 읽는 짧은 수명의 알림 전용 JWT를 받는다. 가입/익명 Auth 사용자 행/개별 DB 세션 행을 매 방문마다 생성하지 않는다.
- JWT는 예약표 범위·권한 세대·짧은 만료(초기안 15분)를 담고 메모리에만 둔다. private Realtime RLS에서 채널과 범위를 확인한다. 예약 테이블 조회·교사 관리 RPC·메시지 발행 권한을 이 JWT에 부여하지 않는다. 서명 비밀값은 서버 secrets에만 두며 VITE_ 변수에 넣지 않는다.
- 공개 Realtime 연결은 교사 로그인용 Supabase 클라이언트와 분리해 인증을 덮지 않게 한다. 임의의 예약표/소유자 채널 접근, 위조·만료 토큰, 공개 JWT로 교사 작업 시도를 검사한다.
- 특별실 알림의 발행/구독은 private 모드로 제한하고 동일 topic의 public 구독이 메시지를 받지 못함을 확인한다. 다른 기능 영향을 조사하지 않고 프로젝트 전체 Realtime 공개 설정을 바꾸지 않는다.
- 비밀번호/공개 토큰 변경 시 accessEpoch를 바꾸고 이후 알림은 새 채널에 보낸다. 옛 채널에는 접근 변경 신호만 보내 화면을 다시 잠그게 한다. 기존 권한으로 새 예약 활동을 계속 받지 못하게 한다.
- 현 프로젝트가 수용하는 서명 방식과 전용 JWT 역할은 구현 전 확인한다. 기존 키를 덮어쓰거나 전역 로그인 정책을 바꾸지 않는다. 별도 키 준비가 필요하면 후속 배포에 포함하며 현재는 설정을 변경하지 않는다. [Realtime 권한](https://supabase.com/docs/guides/realtime/authorization), [JWT 서명키](https://supabase.com/docs/guides/auth/signing-keys).

### 메시지와 재조회

권한 확인된 **해당 실/주 채널**에는 eventId·operationId·주간 버전과 생성/수정된 최소 셀 DTO 또는 삭제 ID를 보낸다. DTO는 기존 공개 표가 읽는 ID·날짜·교시·학급/용도 라벨·행 버전만 포함한다. 비밀번호·비밀번호 해시·사용자 정보·공개 링크는 넣지 않는다. 예약 라벨은 원래 표의 입력값이므로 이 값도 허가된 동일 범위에서만 전송하고 로그에 남기지 않는다.

- 일반 예약 알림은 셀 데이터를 캐시에 직접 적용한다. 정상 수신마다 50개 화면이 각각 DB를 재조회하지 않게 한다.
- 내 응답과 내 알림은 operationId/주간 버전으로 한 번만 적용한다. 알림을 무조건 버리지 않고, 다른 변경이 사이에 있었다면 버전 연속성을 확인한다.
- 단조 증가하는 실/주 버전은 작은 room_week_state에 저장한다. snapshot은 예약과 같은 SQL 시점의 주간 버전을 반환한다. 구독을 먼저 확인하고 조회 동안 받은 이벤트를 버퍼에 둔 뒤 snapshot 버전 이후만 반영한다.
- 중복/과거 버전은 무시하고 버전이 건너뛰면 해당 범위 snapshot을 한 번 읽는다. 삭제→같은 칸 재생성과 응답 역전도 버전으로 판별하며 삭제는 해당 ID에만 적용한다.
- 메타/학사일정 알림이나 버전 누락에 필요한 조회만 250~500ms로 병합한다. 요청 중 새 알림은 뒤따르는 확인 한 번으로 처리한다. 일반 셀 알림의 화면 적용은 읽기 디바운스를 기다리지 않는다.
- 숨겨진 탭은 데이터 재조회를 멈추고 무효화만 기록한다. 복귀할 때 한 번 확인한다.
- 안정 연결에서 변경이 없으면 전체 표를 매분 읽지 않는다. **5분 간격의 선택 실·주 확인**은 알림 유실 복구용으로만 둔다. JWT 갱신은 필요할 때 이 응답에 합쳐 별도 반복 요청을 추가하지 않는다.
- 이벤트 수신 뒤 현재 표 반영까지 p95 2초 이내를 가상 자료의 목표로 둔다. 실제 시험 환경에서 확인해야 하며 성능 보장이 아니다.
- 재조회 실패는 마지막 확인 시각과 오류를 표시하고 초안을 보존한다. 저장은 DB에서 최신 상태/버전을 검증하므로 화면 캐시가 덮어쓰기 권한이 되지 않는다.

### 알림 발행의 쓰기 비용

1차안은 DB 트랜잭션과 함께 Broadcast 메시지를 기록한다. 정상 커밋된 변경만 전달되고 DB 롤백은 메시지도 남기지 않게 검증한다. 예약은 statement-level 변경 집계, 메타/휴관은 예약표 단위 갱신, 학사일정은 RPC 완료 지점을 사용해 기존 직접 RLS 관리 쓰기도 놓치지 않는다. 트리거와 RPC에서 중복 발행하지 않는다.

단일 예약은 해당 실/주 메시지 1건을 기본으로 한다. 여러 셀 변경은 같은 실/주 안에서 합친다. 52주 반복은 최대 52개 주간 상태 갱신과 52개 범위 메시지를 만들 수 있다. 각 화면은 가입한 주의 메시지만 받는다. 이 비용을 숨기지 않고 비교하며, 필요하면 반복만 하나의 예약표 범위 변경 신호+해당 주 재조회로 바꾸는 안과 비교한다. 소유자 요약 변경 메시지가 추가되는 수도 별도로 센다.

**DB Broadcast와 주간 상태도 추가 쓰기다.** 일반 저장에서 예약 행 외에 주간 상태 1회와 메시지 1건이 생긴다. 대신 정상 수신자의 재조회 및 그 요청 제한 카운터 쓰기를 없앤다. 공식 문서상 realtime.messages에 메시지를 저장하고 정리하며 private 채널 가입/권한 확인도 비용이 있다. 읽기 절감과 새 쓰기를 같은 부하에서 비교한다. [Broadcast 저장·권한 동작](https://supabase.com/docs/guides/realtime/broadcast).

DB 메시지/WAL 비용이 병목으로 확인되면 서버의 커밋 후 REST Broadcast를 비교한다. 이 경우 저장 성공과 알림 성공을 구분하고, 유실은 재연결/5분 확인으로 복구한다. 전환 시 모든 관리 쓰기 경로가 서버 발행을 지나도록 해야 하므로 초기안보다 구현 범위가 커진다. REST 방식도 네트워크·Realtime 비용이 있으며 무료 I/O로 계산하지 않는다.

## 3. 캐시와 저장 결과 사용

- 캐시는 브라우저 탭 메모리의 작은 LRU로 시작한다. 예: 최대 8개의 실·주 snapshot. 키는 사용자/공개 권한 범위·예약표·실·주·스키마 버전을 포함한다.
- 미리 읽기는 기본으로 하지 않는다. 모든 실·이전/다음 주를 자동으로 내려받지 않는다. 로그아웃·권한 변경·401/403·예약표 삭제 시 해당 캐시를 지운다.
- 실/주 채널을 떠났다가 돌아오면 캐시를 즉시 보여 주되 구독 후 버전을 한 번 확인한다. 캐시 적중만으로 최신이라고 표시하지 않는다. 연결 채널은 현재 실/주와 메타로 한정하고 캐시 8개에 대응하는 8개 구독을 계속 유지하지 않는다.
- 캐시된 표와 최신 확인 상태를 구분한다. 목록 복귀·인쇄·실/주 이동에서도 같은 조회 상태 규칙을 적용한다.
- 단일 저장 응답의 실제 예약 ID·행 버전·주간 버전·내용으로 한 셀만 갱신한다. 취소 응답은 삭제한 ID에만 적용해 같은 칸에 새로 생성된 예약을 지우지 않는다. 직전 주간 버전과 맞으면 재조회 없이 확정하고, 다른 변경 누락이 있으면 해당 주만 복구한다.
- 반복 결과는 실제 생성 행·건너뛴 날짜를 돌려준다. 현재 캐시가 가진 주에 해당하는 행만 반영하고, 미래 52주를 다시 읽지 않는다.
- 오래된 쓰기 응답이나 주간 응답이 더 최신 예약 버전을 덮지 않게 한다. 실패 시 다른 사용자의 갱신을 포함한 전체 배열을 되돌리지 않는다.
- Edge 인스턴스 전역 메모리는 일관성 있는 공용 캐시로 가정하지 않는다. 보호된 예약 응답을 공용 CDN 캐시에 저장하지 않는다.
- 조건부 확인은 실/주 버전과 메타/학사일정 버전을 사용한다. 같으면 예약 상세 조회를 생략한다. 요청 제한 카운터·권한 확인·버전 읽기는 남아 있으므로 변경 없는 확인도 I/O 0으로 보고하지 않는다. 전체 예약 배열을 읽어 만든 fingerprint를 읽기 절감으로 계산하지 않는다.
- room_week_state는 빠른 셀 직접 동기화의 누락/순서 검증 때문에 최소 스키마에 포함한다. 변경이 있을 때만 해당 실/주 행을 한 번 증가시키고 조회마다 생성/수정하지 않는다. 캐시 조건 확인에도 활용해 주간 버전이 같으면 예약 행 조회를 생략한다. 별도의 전체 변경 로그·셀별 tombstone 테이블은 기본안에 추가하지 않는다.

## 4. 필요한 쓰기만 원자적으로 수행

- 예약 행의 revision은 해당 행 수정과 함께 증가시킨다. 모든 예약마다 예약표 행의 버전·updatedAt·수량 카운터도 갱신하는 구조를 만들지 않는다.
- metadataRevision/calendarRevision/accessEpoch는 관련 운영 정보가 실제로 바뀔 때만 예약표의 기존 수정과 함께 변경한다. 날짜와 학기말의 일별 계산은 캐시 범위에 한국 날짜도 포함한다.
- 동일 라벨/설정 재저장은 기대 상태를 확인한 후 변경 없음으로 반환하여 실제 UPDATE와 Broadcast를 생략한다.
- 예약은 조건부 update/delete, 빈 칸은 유니크 제약, 반복은 집합 INSERT ... ON CONFLICT DO NOTHING ... RETURNING으로 처리한다. 교시·요일·종료·휴관·비밀번호/실 소속 검증을 유지한다.
- 예약표 설정 보호는 공유 잠금, 예약 행의 변경은 해당 셀 범위로 설계해 다른 실 예약을 전부 직렬화하지 않는다. 같은 실/주의 마지막 버전 증가·알림은 주간 상태 행에서 짧게 직렬화한다. 관리 종료/휴관/일정 변경은 같은 예약표에 배타 잠금을 먼저 잡는다. 예약 셀→주간 상태의 정렬된 잠금 순서와 기존 직접 쓰기/새 RPC의 혼용도 검사한다.
- 잠금 자체도 물리 쓰기를 유발할 수 있으므로 비용이 0이라고 가정하지 않는다. [PostgreSQL 행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS).
- 반복의 동일 작업 재시도는 중복 생성과 수량 변화를 막는다. 저장 결과 로그가 필요하면 반복 작업당 1건의 최소 결과와 한정된 보관/정리 규칙으로 시작한다. 모든 조회/단일 예약에 새로운 영구 작업 로그를 붙이지 않는다.
- 학사일정은 기존 행과 비교해 실제 차이만 한 트랜잭션에서 적용한다. NEIS 실패는 0건의 자료 변경, 동일 응답은 0건의 행사 DML/변경 알림을 목표로 한다. 학교/소유자 최종 확인과 다른 기간 보존을 유지한다.
- DB 기반 요청 제한은 실패 시 차단을 유지한다. Edge 메모리 카운터로 바꾸면 여러 인스턴스에서 우회할 수 있으므로 대체하지 않는다.
- 기존 요청 제한 테이블의 키 누적과 UPDATE 빈도·dead tuples도 측정한다. 만료 키 정리가 필요하면 작은 배치와 부하가 낮은 주기를 설계하며, 허용 기준/차단 정책을 완화하지 않는다.

## 5. 인덱스·스키마 도입 기준

초기 필수안: 예약 행 revision, 운영 정보 revision/권한 세대, 실/주 상태의 단조 버전, 필요한 RPC·트리거·private Realtime RLS. 주간 상태는 (room_id, week_start)를 키로 하고 실/예약표 소속과 소유자 권한을 검증한다. 익명/알림 JWT가 직접 상태 테이블을 읽거나 쓰지 못하게 한다. 새 마이그레이션으로만 추가한다. 실/주 상태는 변경이 있었던 범위만 보유하고 revision 값 자체를 별도 인덱싱하지 않는다. 수량 캐시·전체 변경 로그·광범위 covering index·Redis·read replica는 자동으로 추가하지 않는다.

인덱스는 기존 조건과 실행계획을 비교한다. 주간 조회에 이미 있는 실/날짜 유니크 인덱스를 중복 추가하지 않는다. 상태/소유자 목록이나 휴관 교차 검색이 실제 병목이면 후보 인덱스를 시험하고 읽기 개선과 예약 쓰기/WAL 증가를 함께 기록한다. 인덱스가 쓰기·저장 공간 비용을 가진다는 점은 [Supabase 인덱스 문서](https://supabase.com/docs/guides/database/postgres/indexes)에도 명시되어 있다.

예약 데이터 보관·영구 파기는 성능 조치로 섞지 않는다. 예전 예약을 지우거나 개인정보 보관 정책을 소급해 I/O를 줄이지 않는다.

## 측정·검증과 수용 기준

### 준비

운영 수치를 현재 알고 있다고 가정하지 않는다. 먼저 가상 자료로 네트워크/DB 호출·반환 행·응답 바이트·실행시간을 재현한다. 허용된 시험 DB에서만 SQL 실행계획·잠금·WAL을 수집한다. 실제 운영 Dashboard/통계 확인은 후속 읽기 작업으로 별도 구분한다.

- 시나리오: 1/3/50실, 빈/대표/최대 주, 1년 이력, 1/10/50개 동시 화면, 실제 변경 0/10/100건, 반복 52주, 교사 목록/진행 업무 동시 진입.
- 같은 데이터·설정·실행시간으로 기존/개선안을 비교한다. 작은 테이블의 합리적인 Seq Scan을 무조건 실패로 판단하지 않는다.
- 브라우저: 요청 수·응답 바이트·중복 요청·새로고침 횟수·알림→화면 p50/p95. Realtime 연결 수·메시지 수·재연결/권한 검사·egress도 함께 수집해 디스크 부담 감소를 다른 비용 증가로 숨기지 않는다.
- DB: pg_stat_statements calls/rows/시간/shared block hit/read/dirtied/written, 사용 가능한 I/O 통계, EXPLAIN (ANALYZE, BUFFERS), 필요 시 WAL 지표, dead tuples·잠금 대기.
- 함수 내부 SQL이 통계에서 보이지 않으면 내부 쿼리 계측 또는 시험 DB 설정으로 분리 측정한다. 최상위 RPC 1회만 세어 성공으로 처리하지 않는다.
- ANALYZE는 실제 실행이다. 쓰기 분석은 가상 시험 DB에서만 하며 운영 자료에는 쓰기 EXPLAIN을 실행하지 않는다. [Supabase 쿼리 통계](https://supabase.com/docs/guides/database/extensions/pg_stat_statements).

### 요청 예산

| 행동 | 1차 설계 목표 | 추가 조건 |
| --- | --- | --- |
| 공개 비보호 첫 화면 | Edge 1회 / DB API RPC 1회 | 내부 SQL·행 수는 별도 계측 |
| 비밀번호 해제 성공 | 해제+첫 주 응답 1회 | 실패 제한과 매 요청 권한 확인 유지 |
| 단일 저장·취소 | 정상은 요청 1회, 성공 후 조회 0회 | 다른 사용자 셀 변경도 알림으로 직접 적용, 누락 버전은 해당 범위 복구 |
| 반복 저장 | 요청 1회, 미래 주 재조회 0회 | 실제 생성·건너뜀과 재시도 결과 일치 |
| 교사 목록 | 요약 1 RPC/페이지 | 예약 라벨·전체 일정 반환 0건, 수량 정확 |
| 진행 업무 | 기존 정상 요약 1 RPC 유지 | 실패 복구의 특별실 요약은 필요한 페이지 수, 상세 라벨 반환 0건 |
| 실·주 선택 | 새 범위의 자료/조건부 확인 1회, 동일 범위 진행 중 요청 1개 | 캐시는 즉시 표시하되 새 채널의 최신 버전 확인, 서버 쓰기 검증 유지 |
| 일반 셀 변경 알림 | 연속 버전이면 재조회 0회 | 셀 패치를 직접 적용, 중복/과거 메시지 무시 |
| 메타/일정 변경·버전 누락 | 관련 범위 재조회 최대 1개 + 필요한 뒤따르는 확인 1개 | 무관한 범위 상세 재조회 0회 |
| 안정 연결·변경 없음 | 보이는 탭의 복구 확인 최대 1회/5분 | 필요한 JWT 갱신 합침, 숨긴 탭 데이터 요청 0회 |

예시: 50개 화면을 8시간 계속 열어 놓으면 60초 갱신은 24,000회, 5분 복구 확인은 4,800회다. **주기 요청만 80% 감소하는 계산**이며 접속 권한 검사·주간 상태/DB Broadcast 쓰기·초기 진입·누락 복구는 별도다. 실제 디스크 I/O/요금 80% 감소라는 뜻은 아니다. 일반 셀 알림은 50개 화면의 DB 읽기를 추가하지 않는 것을 목표로 한다. 변경이 매우 잦을 때 메시지 수·주간 상태 잠금·누락 복구 fan-out도 비교한다.

필수 알림 회귀: snapshot과 구독 시작 경쟁, 중복/순서 역전/버전 누락, 삭제 후 재생성, 내 응답과 알림의 경쟁, 서버 롤백, 52주 반복, 재연결/숨김/복귀, 비밀번호 변경·만료·타 예약표/private-public 채널 접근 거절. 모의 WebSocket/SQL 검사를 실제 Supabase Realtime 권한 검증으로 보고하지 않는다.

완료 조건: 기존 18개 결함의 회귀 기준 통과 + 위 요청 예산 + 실제 SQL 읽기 범위 감소 + 쓰기/WAL/잠금 비교. 정합성과 빠른 갱신을 통과해도 I/O 총량이 늘면 원인을 적고 배포 전에 설계를 조정한다. 정량 절감률은 측정 후 보고한다.

## 구현 순서와 배포 경계

1. 기준 계측과 P1 오류/초안 보호를 먼저 준비한다. 동시에 전체 조립 사용처를 요약/선택 범위 조회로 분리하고 기존 집계 의미를 보존한다.
2. 원자 쓰기 RPC·행 버전·실/주 버전·반환값으로 저장 후 조회를 제거한다. 메타 변경 경로와 관리 잠금 규칙도 함께 연결한다.
3. private Broadcast와 알림 전용 권한을 시험 환경에서 검증한다. 셀 변경 직접 적용·버전 누락 복구·요청 병합·5분 확인을 붙인다. JWT/권한/외부 설정 변경은 이 단계의 명시적 배포 항목이다.
4. 행사 차이 적용과 관리 실패 복구를 완료한다. 목록 요약·영향 수·인쇄의 최신성도 확인한다.
5. 기존 기능 계획의 모바일/접근성 → A4 출력 → 날짜/탐색 순서로 진행한다. 전체 화면과 AI 모의 검토의 2차 수정·재검증 요구를 유지한다.
6. 성능·보안·동시성·E2E 검사 후 승인된 배포 범위에서만 필요한 secrets → 새 migration → 대상 Edge Functions → 프런트엔드를 적용한다. 서명키/RLS/Realtime 설정 준비를 별도 확인하고 기존 키를 덮어쓰지 않는다.

진행 업무 복구의 특별실 공급자를 경량화하면 [기존 공급자 검사](../../../tests/unit/activeWorkProviders.test.ts)·[요약 검사](../../../tests/unit/activeWorkSummary.test.ts)·[흐름 검사](../../../tests/e2e/active-work.spec.ts)와 전체 단위를 포함한다. 관련 공통 변경은 shared 범위 커밋으로 분리한다. 예: perf(shared): 진행 업무 특별실 복구 조회 경량화. 제품 수정·원격 DB 확인·배포는 아직 수행하지 않았다.
