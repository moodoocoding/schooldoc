## 목표와 기본 정책

우선 예약의 성립과 조회 상태를 믿을 수 있게 만들고 전체 자료 조립을 필요한 범위의 조회로 분리한다. 저장 반환값과 범위별 변경 알림을 사용해 반복 재조회를 줄인다. 다음으로 관리 오류 복구·모바일 사용·출력을 고치고, 마지막에 많은 실과 먼 날짜의 탐색을 개선한다. API 요청 수·읽는 행/블록·쓰기를 함께 측정하며 RPC 1회만으로 I/O 최적화가 완료됐다고 판단하지 않는다.

1. 공개 토큰과 필요한 비밀번호를 확인한 사용자가 서로 예약을 수정·취소하는 공유 시트 정책을 유지한다. 예약별 계정·소유자 인증을 새로 도입하지 않는다.
2. 이미 입력한 초안과 기존 예약은 오류·외부 갱신·운영 설정 축소로 삭제하지 않는다. 교시·토요일을 다시 늘리면 숨겨졌던 예약이 복원되어야 한다.
3. 과거 날짜의 신규 예약·정정·취소는 현재 동작을 유지한다. 과거 신규 예약 금지는 별도 정책 변경으로 다룬다.
4. 신규 예약은 현재 교시 수와 월~금/선택한 토요일 운영 범위를 따른다. 설정 밖에 이미 있는 기록의 조회·정정·취소는 신규 생성 검증과 구분한다. 종료·휴관에 대한 기존 쓰기 제한은 유지한다.
5. 기본 출력 범위는 현재 선택한 특별실의 현재 주다. 전체 실 일괄 출력은 이 결함 수정의 필수 범위에서 제외한다.
6. 공개 갱신을 위해 익명 사용자에게 예약 테이블 직접 조회 권한을 열지 않는다. 기존 토큰·비밀번호 검증 경로와 교사 소유자 RLS를 유지한다.

## 1. 9교시·조회 상태·실패 초안

대상: [공개 함수](../../../supabase/functions/special-rooms-public/index.ts), [공개 화면](../../../src/features/specialRooms/PublicSpecialRoomsPage.tsx), [주간 표](../../../src/features/specialRooms/SpecialRoomWeekGrid.tsx), [입력 시트](../../../src/features/specialRooms/BookingSheet.tsx), [낙관적 반영](../../../src/features/specialRooms/specialRoomsOptimistic.ts).

- 공개 함수의 전역 교시 범위를 DB와 같은 1~9로 맞춘다. 잘못된 값 0·10·소수·문자열 경계도 검사한다. 예약표별 운영 범위는 2에서 별도로 검증한다.
- 조회마다 요청 세대와 토큰·주간 범위 키를 붙인다. 이전 주/비밀번호/토큰의 응답은 현재 화면에 반영하지 않는다. 전체 조회와 가벼운 갱신이 같은 규칙을 사용한다.
- 초기 로딩·확인된 빈 주·현재 주 로딩·오류·최신 확인 실패를 구분한다. 조회 실패를 빈 배열로 바꾸지 않는다. 이전 주를 유지하면 이전 주의 제목도 유지하고 조회 중인 주를 별도로 표시한다.
- 실패 화면에 다시 시도를 제공한다. 해당 주의 성공 응답을 받기 전에는 예약 가능한 빈 칸으로 조작할 수 없게 한다. 다른 주 데이터에 새 주 날짜를 붙이지 않는다.
- 초안은 예약표·실·날짜·교시별로 탭 메모리에 보관한다. 저장 결과를 받기 전에 입력 시트를 닫거나 값을 지우지 않는다. 외부 예약 갱신은 현재 예약 정보만 갱신하고 입력 초안을 덮지 않는다.
- 낙관적 반영을 유지한다면 실패한 셀의 해당 작업만 되돌린다. 예약 배열 전체를 예전 복사본으로 복원해 다른 갱신을 지우지 않는다. 서버 저장 성공 뒤 재조회만 실패한 경우에는 저장을 취소한 것처럼 되돌리지 않는다.
- 목록은 요약만, 예약표는 선택한 실/주만 조회하는 모델로 분리한다. 진행 업무의 기존 정상 요약 RPC는 유지하고 실패 복구의 특별실 부분에도 요약 조회를 사용한다. 운영 설정 축소/휴관 영향 수는 해당 입력이 유효해졌을 때 서버 집계로 구해 기존 안내를 유지한다. [상세 조회 설계](db-optimization-plan.md)를 따른다.

필수 재현: 10/5 응답이 10/12 응답보다 늦게 도착, 다음 주 조회 503, 초기 조회 503, 저장 실패 후 같은 초안 재시도, 서버 저장 성공 뒤 조회 실패. 오류 안내와 다시 시도도 키보드로 사용할 수 있어야 한다.

### 저장 계약

- 예약 행에 단조 증가하는 버전을 추가하는 새 마이그레이션을 만든다. 기대 상태는 빈 칸 또는 예약 ID+서버 버전이다. 수정/취소는 요청이 본 상태가 현재 상태와 같을 때만 수행한다.
- 기대 버전은 편집을 열 때의 서버 응답에서 확보한다. 낙관적 반영의 클라이언트 updatedAt이나 pending ID를 비교 기준으로 보내지 않는다.
- 예약이 바뀌었으면 409와 기계적으로 구분 가능한 충돌 코드를 반환한다. UI는 내 초안과 현재 예약을 함께 보여 주고, 사용자가 현재 내용을 확인하여 다시 저장할 때 새 기대 버전을 보낸다.
- 단일 저장은 서버가 확정한 예약 ID·버전·내용을 반환한다. 취소도 실제 성공/충돌을 구분한다. 저장소가 모든 오류를 일반 Error 문구로만 바꾸지 않도록 오류 종류를 전달한다.
- 재시도에는 동일한 작업 ID를 사용한다. 응답 유실 뒤 반복 실행해도 중복 생성하거나 성공 수를 바꾸지 않게 처리한다. 모든 조회/단일 예약에 영구 로그를 추가하지 않는다. 반복 결과 보관이 필요하면 작업당 1건의 최소 결과와 보관/정리 규칙을 함께 정한다.
- 저장/취소/반복 응답으로 해당 셀과 이미 가진 주간 캐시를 갱신한다. 내 응답과 알림은 작업 ID/주간 버전으로 한 번만 적용한다. 정상 성공 후 전체 표/미래 주 재조회는 생략하고 다른 변경 버전이 누락되었을 때만 해당 범위를 복구한다.

### 트랜잭션과 운영 검증

- 읽고 나서 별도 update/delete를 호출하는 구조를 DB의 조건부 변경 RPC로 바꾼다. 조건부 update/delete의 실제 변경 행 수를 검사하며, 빈 칸 생성은 기존 유니크 제약도 유지한다.
- 예약표 설정은 공유 잠금으로 보호하고 예약 행의 조건부 변경을 해당 셀 범위로 수행한다. 최신 토큰·비밀번호·실 소속·종료·휴관·교시·요일을 검증한다. 다른 실 예약을 불필요하게 직렬화하지 않으며 반복 후보·휴업일 검사도 원자적 처리에 포함한다.
- 교사 상태/설정 변경은 현재 브라우저의 RLS 경로에서 직접 일어난다. 관련 관리 변경은 예약표 배타 잠금을 먼저 잡도록 RPC 또는 트리거로 연결한다. 휴관 삽입/제거와의 경쟁도 포함하며 동일한 잠금 순서를 검증한다.
- 내부 공개 쓰기 RPC는 서비스 역할만 실행하게 한다. 관리 RPC를 만들면 소유자 검사를 포함한다. RLS·권한·고정된 search_path와 직접 익명 호출 차단을 SQL 검사에 포함한다.
- 신규 생성은 현재 운영 교시/요일을 검증한다. 기존 숨겨진 기록은 보존하고, 기존 기록 정정/취소와 신규 생성을 별도 분기로 처리한다. 날짜 문자열은 실제 유효한 달력 날짜인지 확인한다.
- 프런트엔드·데모·서버가 재사용할 순수 규칙은 기존 [_shared 구조](../../../supabase/functions/_shared/classroomRoles.ts)를 참고해 분리한다. 종료 후 반복도 데모에서 거절한다. 한국 날짜 계산은 여기서 준비하되 기존 다른 기능의 시간 정책을 함께 바꾸지 않는다.

### 반복 결과

반복은 기존 예약을 덮지 않고 계속 개별 예약으로 저장한다. 실제 INSERT RETURNING으로 생성 날짜를 확정하고, 경쟁으로 채워진 칸은 skippedTaken에 포함한다. 휴업일·휴관 건너뛰기도 실제 처리 결과를 기준으로 안내한다. 4주 중 1주를 다른 요청이 먼저 차지하면 내 결과는 생성 3건·예약 충돌 1건이어야 한다.

필수 재현: 빈 칸 동시 생성, 같은 버전 동시 수정/취소, 삭제 후 같은 칸 재생성, 작성 중 외부 변경, 반복 경쟁, 저장과 종료/휴관/설정 변경 경쟁, 응답 유실 후 같은 작업 재시도. 모의 DB 검사와 실제 PostgreSQL 다중 연결 검사의 결과를 구분한다.

## 3. 운영 정보 갱신·관리 오류·학사일정 교체

대상: [공개 화면](../../../src/features/specialRooms/PublicSpecialRoomsPage.tsx), [관리 화면](../../../src/features/specialRooms/SpecialRoomsManagePage.tsx), [운영 정보 폼](../../../src/features/specialRooms/BoardInfoCard.tsx), [휴관 카드](../../../src/features/specialRooms/ClosureCard.tsx), [저장소](../../../src/features/specialRooms/specialRoomsRepository.ts), [학사일정 유틸](../../../src/features/specialRooms/specialRoomsSchoolDays.ts), [관리 함수](../../../supabase/functions/special-rooms-admin/index.ts).

- 초기 응답은 메타와 선택 실/주를 함께 제공한다. 이후에는 알려진 운영/일정 버전과 실제로 달라진 정보만 제공하고 선택 범위 외 예약은 읽지 않는다. 하나의 SQL 스냅샷으로 메타와 예약의 시점이 섞이지 않게 한다.
- private Broadcast를 주 동기화로 사용한다. 공개 사용자도 토큰·비밀번호 검증 후 제한된 알림 전용 권한으로 연결한다. 선택 실/주 채널에 기존 표에 표시할 최소 셀 DTO·작업 ID·주간 버전을 전달하며 비밀번호·사용자 정보·공개 링크는 넣지 않는다.
- 연속 버전의 셀 변경은 재조회 없이 적용한다. 메타/일정 변경이나 버전 누락의 복구 조회만 250~500ms로 병합한다. 내 응답/알림은 한 번만 적용하고 무관한 실/주는 다시 읽지 않는다. 수동/복귀/재연결 갱신과 보이는 탭의 5분 유실 복구 확인을 제공하며 JWT 갱신을 필요한 응답에 합친다. 60초 전체 갱신은 사용하지 않는다.
- 실패/429 지연 재시도, 마지막 확인 시각, 연결 중 받은 변경 처리와 초안 보존을 포함한다. [알림 권한·쓰기 비용 설계](db-optimization-plan.md)를 함께 적용한다.
- 현재 제한은 같은 IP·토큰·행동별 metadata 60회/분, week 120회/분이다. 조회도 제한 카운터 UPSERT를 수행하므로 알림/복귀 요청 집중·50개 탭·높은 변경 빈도를 시험한다. 요청 병합과 범위 축소를 먼저 적용하고 제한값을 올리는 것으로 해결하지 않는다.
- 익명 전역 Postgres Changes를 사용하지 않고 실/주 private Broadcast RLS와 알림 전용 JWT를 실제 시험 환경에서 검증한다. 주간 버전과 DB 알림도 추가 쓰기이므로 같은 범위의 변경을 묶고 52주 반복의 최대 52개 버전/범위 알림 비용을 계측한다. 서버 쓰기 검증은 알림/갱신 성공과 무관하게 즉시 적용한다.
- 관리 조회의 없음·권한 오류·통신 실패를 구분한다. 상태 변경·휴관 해제·링크 복사는 await/catch/busy/재시도와 정확한 성공 피드백을 제공한다.
- 관리 폼은 외부 변경 시 수정하지 않은 필드만 갱신한다. 수정 중인 필드는 보존하고 충돌을 알린다. 저장은 기대 버전을 확인해 오래된 전체 폼이 최신 교시·토요일 설정을 되돌리지 않게 한다.
- NEIS 응답을 검증한 후 기존 행사와 실제로 다른 행만 한 트랜잭션에서 삽입/수정/삭제한다. 같은 응답이면 행사 DML과 변경 알림을 생략한다. NEIS 호출 중에는 DB 잠금을 잡지 않으며 쓰기 실패 시 이전 일정과 다른 기간이 보존되어야 한다.
- NEIS를 기다리는 동안 학교가 바뀌면 이전 학교의 결과를 새 학교 일정으로 적용하지 않는다. 소유자와 대상 학교 코드를 최종 저장 시 다시 확인한다.
- 학교 연결 해제/학교 변경 실패 후 옛 일정이 어떻게 남고 표시되는지는 추가 재현 후 결정한다. 리뷰에서 소스만 확인한 위험을 확정 결함으로 계산하지 않는다.

필수 재현: 열린 공개 화면에서 종료·재개·휴관·운영 설정 변경, 폼 수정 중 다른 창의 변경, 상태/해제/클립보드 실패, 일정 교체 중 INSERT 실패, 정상 빈 NEIS 응답, 다른 기간 보존, 학교 변경과 느린 NEIS 응답 경쟁.

## 4. 모바일·접근성·전체 화면

대상: [입력 시트](../../../src/features/specialRooms/BookingSheet.tsx), [주간 표](../../../src/features/specialRooms/SpecialRoomWeekGrid.tsx), [공개 화면](../../../src/features/specialRooms/PublicSpecialRoomsPage.tsx), [관리 화면](../../../src/features/specialRooms/SpecialRoomsManagePage.tsx), [기능 색상과 인쇄 CSS](../../../src/index.css).

- 대화상자에 화면 높이 기준 최대 높이와 의도적인 내부 스크롤을 둔다. 확대·낮은 높이에서 닫기·저장·반복 결과까지 키보드로 접근 가능하게 하고 포커스 복귀를 유지한다.
- 모바일 표는 대표 학급명 6학년1반을 식별할 수 있도록 두 줄 표시·글자 크기·여백을 조정한다. 긴 내용은 상세 보기를 제공하며 종료된 읽기 전용 상태에서도 내용을 확인할 수 있게 한다.
- 많은 실은 압축 선택 UI로 바꾸되 6에서 최종 탐색을 완성한다. 일반 3실 화면에서는 표가 첫 화면에 오도록 밀도를 유지한다.
- 탭을 유지하면 방향키·Home/End·roving focus·tabpanel 관계를 구현한다. 실제 탭이 필요 없는 부분은 의미에 맞는 선택 버튼/선택 요소로 정리한다.
- 날짜·교시·오늘·저장 상태 색 대비와 포커스 표시를 수정한다. 기능 전용 토큰을 우선 조정하고 공통 색상을 바꾸면 다른 기능 화면도 확인한다. 색만으로 예약/빈 칸/휴관/종료를 구분하지 않는다.
- 관리 카드의 높이를 서로 억지로 늘리지 않게 해 대표 명단에서 큰 공백과 열 균형을 개선한다. 문서가 세로 스크롤을 맡는 기존 앱 규칙을 유지한다.

구현 전후에 [웹디자인](../../../pro/web-designer.md)·[UX](../../../pro/ux-designer.md)·[UI](../../../pro/ui-designer.md)의 판단·근거·남은 위험을 기록한다. 1차 구현 뒤 여섯 독립 관점(정보 위계/밀도, 비전문 사용자/전자칠판 흐름, 접근성/반응형·상태)의 AI 모의 평가를 각각 기록하고 요구를 반영한 2차 수정과 재검증을 마친다. 이는 실제 전문가 6명이나 교사 승인이 아니다.

전체 화면 확인: 공개 320/390px, 교사 1366px, 전자칠판 모사 1920px, CSS 200%, 390×568px, 빈/대표/최대 자료, 짧은/긴 이름, 예약/미예약/휴관/종료/로딩/오류/충돌. 작은 영역 캡처나 Axe 통과만으로 시각 검토를 대신하지 않는다. 실제 모바일 키보드·전자칠판 하드웨어는 미검증이면 그대로 남긴다.

## 구현·배포의 분리와 완료 판정

1. 구현 직전에 git 상태·사용자 변경·관련 소스·하위 AGENTS를 확인한다. 새 마이그레이션 번호는 다른 브랜치/워크트리와 중복을 확인한 뒤 정한다. 적용된 기존 이력은 수정하지 않는다.
2. 먼저 로컬 코드·SQL·검사·전체 화면/PDF 증거를 완성한다. 리뷰 항목별로 수정/검증 완료 또는 미검증 이유를 기록한다. 모의 검사는 모의로 표시한다.
3. 원격 적용이 요청된 경우에만 linked 이력을 비교하고 알림 전용 JWT의 서명/권한 준비 → 필요한 secrets → 새 DB 마이그레이션/private Realtime RLS → special-rooms-public/special-rooms-admin 대상 지정 배포 → 프런트엔드 순서로 진행한다. 프로젝트 전역 로그인 방식과 기존 키를 임의로 변경하지 않는다.
