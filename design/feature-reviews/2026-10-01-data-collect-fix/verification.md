# 자료 수합 DB 최적화 수정·실제 검증 보고서

## 결과와 검증 경계

2026-10-01~10-02, 전용 브랜치 `codex/fix-data-collect-db-io`에서 이전 리뷰 D01~D17의 수정안을 구현했다. 공유 checkout과 main을 바꾸지 않았으며, 작업 파일은 전용 관리 워크트리에 보관한다. 이 보고서는 구현·검증 기록이며 이전 리뷰의 결함 관찰 assertions를 수정 성공 검사로 재사용하지 않았다.

사용자는 Supabase 시험 환경 제공 대신 **앱의 실제 Chrome 검증 우선**을 선택했다. 설치된 **Google Chrome 154.0.8037.58**을 Playwright의 `channel: 'chrome'`으로 직접 실행하여 입력·선택·클릭·페이지 이동·재접속·키보드 파일 선택·다운로드를 제어했다. 별도 headed Chrome에서도 복구, 재제출 금지, 설정 명단, CSS 200% 흐름을 조작했다. Chrome 화면 캡처와 실제 저장한 파일을 이 폴더에 보존한다.

브라우저는 `127.0.0.1:4183`의 개발용 데모 앱과 가상 자료를 사용했다. 이 Chrome 검증을 원격 Supabase Auth/PostgREST/Storage 검증으로 간주하지 않는다. 별도로 **실제로 실행한 PostgreSQL 18.4**에 필요한 기존 마이그레이션과 새 마이그레이션을 적용해 SQL 동시성·롤백·권한·실행 계획을 확인했다. 이 PostgreSQL도 원격 Supabase 프로젝트가 아니다.

| 진행 업무 | 전체 과거 제출의 DISTINCT 집계 대신 현재 제출 부분 인덱스로 집계 |

기존 admin의 전체 조회 액션은 이전 클라이언트 호환을 위해 남겼다. 새 교사 화면은 제한 조회 API를 사용한다. 기존 서버 암호화 키, RLS 소유자 격리, 비밀번호 검증과 개인정보 보관 기산점은 유지한다. 배포 파일은 30MiB, 제출 파일은 50MiB로 브라우저와 서버가 같은 규칙을 공유한다.

업로드는 개인정보가 없는 UUID 경로에 예약한다. 공개 업로드 준비에서는 아직 제출 대상 행을 만들지 않는다. 실패하거나 만료된 임시 파일은 예약/재시도 기록을 남기며, 교사의 명시적 임시 업로드 정리에서 최대 50건씩 처리한다. 확정 RPC와 정리는 동일한 예약 행의 잠금·조건부 UPDATE로 경쟁하므로, 확정된 예약은 정리 권한을 얻지 못한다. Storage 삭제 확인 후 예약과 정리 기록을 제거한다. 기존 제출 자료를 자동 파기하거나 기존 고아 파일을 추측해 일괄 삭제하지 않는다.

### 실제 로컬 SQL 관찰

가상 대상 2,000명과 과거 버전을 포함한 파일 행 9,037개에서 다음을 관찰했다. 원본 수치는 [postgres.json](postgres.json)에 보존한다.

- 새 현황 첫 페이지 51행의 JSON: **18,473 bytes**.
- 비교용 전체 파일 행 JSON: **3,961,616 bytes**.
- `EXPLAIN (ANALYZE, BUFFERS)`에서 이름/구분 검색이 두 GIN 인덱스를 사용하고, 현재 건수 집계가 `data_collection_files_one_current` 부분 인덱스를 사용했다.
- 30명 동시 신규 제출에서 번호 1~30 중복 없음. 동일 요청 8회 동시 재전송은 파일 행 1개. 같은 대상의 6회 동시 재제출은 중복 버전 없이 현재 1개.
- 대상 UPDATE와 파일 INSERT에 실제 실패 trigger를 주입했을 때 이전 현재 버전/상태를 보존하고 신규 유령 대상을 남기지 않았다.
- 제출 확정과 예약 취소 12회 경합은 확정 6/취소 6으로 나뉘었고, 확정 시 정리 권한 없음·취소 시 파일 행/신규 대상 없음 조건을 모두 만족했다.
- 익명 역할은 업무·대상·파일·예약·정리 테이블에서 0행, authenticated 역할은 관리 RPC 실행 거부, service_role은 확정 RPC 실행 허용.
- 만료 기술 기록 2,001행 중 정확히 1,000행만 정리하고 같은 분의 반복 호출은 다시 정리하지 않았다. 현재 카운터 5는 유지했다.
- 학교 공용 IP를 나타내는 동일 키의 30명 요청은 허용하고 개별 키 반복은 제한했다. 실제 학교 네트워크 HTTP 부하 검사는 하지 않았다.

두 JSON은 반환 필드와 조회 범위가 다르므로 과금 절감률로 환산하지 않는다. **원격 Supabase 디스크 I/O·egress·요금은 측정하지 않았다.** 인덱스와 예약/제한 행의 쓰기 비용도 있으므로 실제 운영량에 따른 검토가 남는다.

## 2026-10-02 목록 캐시·실시간 마감 후속 보완

추가 점검에서 확인한 두 미수정 항목을 보완했다. 목록 화면의 수동 새로고침은 이후 모든 조회에 영향을 주던 `refresh > 0` 조건을 제거하고, 다음 조회 한 번에만 강제 조회 플래그를 소비한다. 다음/이전 이동은 유효한 15초 페이지 캐시를 재사용하며, 버튼을 다시 누르면 다시 조회한다. 실제 자료 변경 알림의 강제 조회는 유지한다.

마감 배지는 화면의 현재 시각을 10초마다 갱신해 계산한다. 시각은 목록 조회 effect의 의존성이 아니므로 타이머가 DB 요청을 만들지 않는다. 숨긴 탭을 다시 표시할 때도 현재 시각을 즉시 갱신한다. 화면을 나가면 타이머와 visibility listener를 해제한다.

### 실제 Chrome과 조회 횟수

`tests/e2e/data-collect-list.spec.ts`는 설치 Chrome의 headed 모드에서 가상 수합을 **실제 UI로 생성**하고 버튼을 조작한다. 데모 저장소의 원래 `Storage.getItem`을 그대로 호출하면서 특정 저장 키의 호출 횟수만 관찰했다. 조회 결과나 API 응답은 대체하지 않았다. 원격 Supabase 요청 수나 디스크 I/O를 측정한 수치는 아니다.

| 조작 | 데모 저장소 누적 읽기 | 판정 |
| --- | --- | --- |
| 21개 가상 수합 생성 후 첫 목록 | 2 | 기준값 |
| 다음 페이지 첫 조회 | 3 | 1회 읽기 |
| 이전 페이지 복귀 | 3 | 캐시 사용 |
| 수동 새로고침 | 4 | 1회 읽기 |
| 이후 다음 / 이전 이동 | 4 / 4 | 추가 읽기 없음 |
| 수동 새로고침을 다시 누름 | 5 | 다시 1회 읽기 |

캐시 이동 구간은 15초 이내에 끝났고, 별도 단위 검사에서 수동 갱신 뒤 다른 페이지 캐시 유지와 정확히 15초가 지난 캐시의 재조회를 확인했다.

마감 검사는 가짜 시계를 쓰지 않고 실제 시간을 기다렸다. 최종 실행은 한국 시각 **00:25:50.308**에 목록을 열어 두고 **00:27:00.000** 마감을 지나 **00:27:00.582**에 `수합 중 → 기한 마감`을 관찰했다. 이 동안 읽기 횟수는 **2 → 2**로 유지됐다. 기한 없는 업무는 `수합 중`, 직접 종료한 업무는 `종료`를 유지했다. 첫 검사의 화면 검토에서 ‘기한 없음’이라는 제목의 자료에 기본 기한이 남아 있음을 발견해, UI로 기한을 제거하는 준비 단계와 기한 없음 assertion을 추가하고 해당 검사를 다시 통과했다.

데스크톱 1366×900과 모바일 390×844의 전체 화면을 확인했다. 두 화면 axe 위반 0개, 모바일 가로 넘침 없음, 두 신규 검사 pageerror 0개다. 일반 탭에서 마감 표시의 갱신 주기는 10초이며 백그라운드 탭의 타이머 지연은 탭 재표시 시각 갱신으로 보완한다. 실제 스크린리더와 원격 계정은 이번 검사 범위 밖이다.
