# 학생 결과 안내 교사 학생 워크플로우 검토 (codex)

> **2026-10-01 당시 기록:** 아래 결론과 R1–R12는 `main`의 `024b2ec`을 검사한 결과이며 현재 미해결 목록이 아니다. 이후 수정과 로컬 재검증은 [구현 기록](implementation.md)에 정리됐고, 총점 저장·설정 변경 뒤 재확인은 후속 커밋 `48de047`에서 보완됐다. 운영 환경 적용 여부는 이 검토서로 확인할 수 없다.

## 결론

파일 가져오기부터 학생 조회·이의 제기·교사 답변·재확인·안내 종료까지 Chrome에서 실제 조작했다. 정상 경로는 이어지지만 **총점 중복 계산, 배포 후 점수 정정 불가, 확인 버튼으로 이의 작성 내용 소실, 다중 페이지 QR PDF 출력 손상**을 우선 수정해야 한다. 단순히 화면을 보기 좋게 만드는 것으로 해결되는 문제가 아니다.

사용자 요청에 따라 이번 작업은 검토만 수행했다. 1인 1역 수정 작업과 분리했으며 제품 코드, 서버 함수, DB, Git 및 배포는 변경하지 않았다. 아래 개선안은 구현 완료 항목이 아니라 별도 개발 작업으로 넘길 요구사항이다.

## 범위와 확인 방법

- 검토일은 2026-10-01이며 시작 기준은 `main`의 `024b2ec`이다. 검토 도중 다른 작업의 1인 1역 변경이 나타났으며 건드리지 않았다.
- Supabase 연결 변수를 비운 독립 로컬 데모 서버를 사용했다. 가상 데이터의 브라우저 저장만 발생했다. 운영 인증·RLS·암호화·원격 Realtime 검증으로 해석하면 안 된다.
- 교사용 목록, 작성, 관리의 현황·접속 정보, 개인 QR 출력, 학생 공개 화면을 연결해 확인했다. 운영 설정은 작성 때의 확인·이의 옵션과 생성 후 변경 가능한 범위를 함께 검토했다.
- 가상 24명 XLSX에는 동명이인 두 명, 확인번호 미입력 한 명, 긴 이름, 전 과목 0점, 다섯 과목과 별도 총점 열을 넣었다. 두 쪽 텍스트 PDF에는 반복 머리글과 가상 학생 여섯 명을 넣었다. 원본과 가져온 전체 학생·과목·점수를 비교했다.
- 교사 화면은 1366px 등 실제 확인된 데스크톱 너비에서 전체 캡처했다. 학생 공개 화면은 384px 캡처와 390px DOM 너비에서 확인했다. 교사 탭의 모바일 너비 적용은 브라우저 제어에서 확인되지 않아 모바일 교사 화면 통과로 보고하지 않는다. 확대 배율·실기기·스크린리더 사용성은 미검증이다.
- 웹디자이너·UX 디자이너·UI 디자이너 프로파일을 먼저 읽고 평가 기준으로 사용했다. 세 프로파일과 아래 여섯 관점은 AI 모의 검토이며 실제 전문가·담임·학생 인터뷰나 승인이 아니다.

## 먼저 수정해야 할 문제

### R1 P1 총점 열을 다시 더한다

원본 첫 학생은 국어 18, 수학 19, 사회 17, 과학 20, 영어 18, 총점 92다. 가져오기에서는 이를 여섯 결과 항목으로 만들고 학생 화면 상단은 **184 / 200**을 표시한다. 총점 항목 자체는 92 / 100으로 표시해 한 화면 안에서 점수 의미가 충돌한다. 비율은 같아도 학생에게 안내하는 실제 총점이 잘못된다.

원인은 학생 공개 화면의 합계가 모든 항목 값을 더하는 것이며, 수치형 총점 열과 독립 과목을 구분하는 규칙이 없다. 관련 위치는 `PublicStudentResultPage.tsx:121`과 파일 분석의 결과 항목 구성이다.

개선 요구는 합계 항목의 의미를 명시적으로 구분하는 것이다. 총점이라는 글자만 보고 모든 자료에서 열을 삭제하지 말고, 가져오기 미리보기에서 총점·참고 수치·독립 점수를 구분하거나 합계 표시 방식을 선택하게 한다. 과목 합계와 원본 총점의 불일치도 경고해야 한다.

근거: [가져오기 분석](evidence/03-xlsx-analysis.jpg), [학생 모바일 전체 화면](evidence/08-student-mobile-total.jpg).

### R2 P1 이의 처리에 필요한 점수 정정 기능이 없다

학생이 국어 18점을 19점인지 확인해 달라고 이의를 낸 후 교사 화면에는 답변 입력만 있다. 학생 결과·배점·피드백·안내 문구·확인 및 이의 옵션을 생성 후 수정할 경로가 없으며, 서버 관리 action도 조회·생성·삭제·상태·답변·토큰 재발급만 제공한다. 새 안내를 다시 만들면 기존 링크·확인·이의 이력의 연속성을 잃는다.

개선 요구는 기존 학생 결과의 정정 경로, 변경 전후 이력, 해당 학생의 재확인 정책을 함께 만드는 것이다. 실제 점수 변경과 단순 설명 답변을 구분해야 한다. 교사 답변을 다시 수정하는 경로도 필요하다. 개인정보 접근은 기존 소유자 검사·암호화 경로를 유지한다.

근거: [교사 재확인 현황](evidence/11-teacher-reconfirm.jpg), `StudentResultsManagePage.tsx:233`, `studentResultsRepository.ts:38`, `student-results-admin/index.ts:125` 이후 action.

### R3 P1 확인 버튼을 누르면 작성 중인 이의가 사라진다

동명이인 두 번째 학생의 개인 링크로 들어가 이의 내용을 쓴 뒤 ‘내용 확인 완료’를 눌렀다. 경고 없이 확인 상태가 되었으며 입력한 내용·이의 제출 버튼이 모두 사라졌다. 완료 이후의 이의 제기·확인 취소·다른 학생으로 종료하는 동작도 없다. 학생은 확인을 단순한 읽음 처리로 이해할 수 있는데 현재 동작은 이의 입력 경로까지 닫는다.

개선 요구는 확인과 이의의 의미를 분리하고, 작성 중인 이의가 있으면 확인 전에 선택을 묻는 것이다. 확인 이후에도 정책에 맞는 이의 제기 또는 확인 취소 경로를 제공해야 한다. 서버는 확인된 학생의 이의 요청을 일률 차단하지 않으므로 UI와 서버의 상태 규칙도 함께 정렬한다.

근거: [확인 후 학생 화면](evidence/13-confirm-drops-dispute-draft.jpg), `PublicStudentResultPage.tsx:131`.

### R4 P1 QR 미리보기와 실제 PDF가 다르다

24명·세 쪽 미리보기의 제목·카드·긴 이름은 보인다. 실제 내려받은 A4 PDF 첫 쪽은 정상이나 두 번째와 세 번째 쪽에는 제목·카드 테두리·안내 문구가 빠지고 마지막 줄 QR 일부가 페이지 밖으로 잘린다. 파일 생성 성공이나 PDF 헤더 검사만으로는 이 문제를 찾을 수 없다.

관련 구현은 각 DOM 페이지를 html2canvas로 캡처하는 `StudentResultsQrPrintPage.tsx:53` 이후다. **정확한 렌더링 원인은 이번 검토에서 확정하지 않았다.** 페이지 캡처 좌표·뷰포트·스크롤·반응형 스타일을 별도로 진단해야 한다.

개선 완료 기준은 1·8·9·24명, 긴 제목·이름, 여러 페이지에서 미리보기와 출력의 구조가 같고 모든 QR이 온전히 출력되는 것이다. 운영 도메인의 실제 QR 스캔은 별도 확인해야 한다.

생성 후 점수와 설정을 고칠 수 없다는 문제는 R2에 통합했다. 같은 결함을 여러 화면의 독립 문제로 중복 집계하지 않는다. R7의 학생 화면 갱신 부재는 교사용 Realtime의 정상 여부와 별개다.

## 검사 결과와 한계

- `npm test -- tests/unit/studentResults.test.ts tests/unit/studentResultsHistory.test.ts tests/unit/studentResultsLoadState.test.ts`: 3파일 27검사 통과.
- `npm run typecheck`: 통과.
- `npm run lint`: 종료 코드 0. 특별실·공통 컴포넌트와 다른 검토 스크립트의 경고 7건이 있다. 이번 검토에서 수정하지 않았다.
- Chrome 수동 시뮬레이션, 전체 화면 캡처, 실제 내려받은 3쪽 A4 PDF 렌더·각 쪽 시각 확인을 수행했다. 테스트 통과와 발견한 UX 결함이 공존한다.
- 확인한 기능 탭의 앱 콘솔에는 런타임 오류를 발견하지 않았다. 데모에서 Supabase가 설정되지 않았다는 예상 경고가 있었다. 전체 외부 확장 프로그램 콘솔의 무오류를 주장하지 않는다.
- 자동 Playwright E2E·운영 Supabase 통합·원격 권한·장애 복구·동시 접속 부하 검사는 실행하지 않았다. 제품 코드를 수정하지 않았으며 브라우저 시뮬레이션은 연결된 Chrome 제어로 수행했다.
- 파일 전달 권한 제한은 기본 파일 선택창으로 처리했다. PDF 다운로드 이벤트를 기다리는 브라우저 제어가 중단되었으나 실제 파일은 정상 저장되어 생성 시각·A4 세 쪽·각 쪽 렌더로 확인했다. 제어 중단 자체를 제품 결함으로 집계하지 않았다.
- 운영 링크의 실제 QR 스캔, 링크 재발급 실행, 영구 삭제 실행은 하지 않았다. 재발급·삭제 경고와 취소만 확인했다.

## 별도 수정 작업에 넘길 순서

1. 총점 의미와 다중 페이지 QR 출력부터 바로잡는다. 가상 원본과 학생 화면·실제 PDF를 함께 비교하는 회귀 검사를 추가한다.
2. 점수·피드백·안내·옵션 수정의 범위와 이력을 설계한다. 기존 공개 링크·응답 의미를 유지하고 변경된 학생만 재확인시키는 정책을 정한다.
3. 확인·이의·답변·재확인 상태를 옵션별로 정렬한다. 작성 중인 이의 보호·확인 실수 복구·조회 종료를 연결한다.
4. 파일 요약의 되돌리기, 새 파일 교체, 초안 보호, 정확한 목록 요약과 키보드 동작을 정리한다.
5. 전체 대표 명단과 학생 모바일·교사 모바일·확대·출력·운영 권한 검증을 분리해 다시 확인한다. 데모 성공을 운영 완료로 보고하지 않는다.
